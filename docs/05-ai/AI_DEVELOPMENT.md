## 1. 核心理念

**工具无关，规范统一。**

本项目不为任何特定 AI 产品维护专属配置。所有 AI 协作规范集中在仓库根目录的 [`AGENTS.md`](../../AGENTS.md)——它遵循开放的 `AGENTS.md` 约定，是一个纯文本、无厂商依赖的格式，任何具备文件读取能力的 AI 编码工具都能直接使用。

这样做的收益：

| 收益 | 说明 |
|---|---|
| 规则单一 | 规范只有一份，不会出现「A 工具知道、B 工具不知道」 |
| 无锁定 | 更换或新增 AI 工具时，无需迁移任何配置 |
| 可审查 | 规则以普通 Markdown 存在，可像代码一样评审与追溯 |
| 长期有效 | 不依赖某产品的配置格式，不会因产品变更而失效 |

## 2. 规则分层

```
AGENTS.md                     ← 唯一权威规范（人 + AI 共用，工具无关）
  └── docs/                   ← 详细文档，按需引用
      ├── 01-product/         产品上下文
      ├── 02-architecture/    技术上下文
      ├── 03-api/             接口契约
      ├── 04-engineering/     工程规范
      ├── 05-ai/              AI 协作方法（本目录）
      ├── 06-decisions/       历史决策（AI 必须尊重，不得违背）
      └── 07-specs/           功能规格（任务的具体输入）
```

**冲突优先级**：`AGENTS.md` > `docs/` > 用户当次指令。若用户指令与 `AGENTS.md` 红线冲突，应指出冲突并请求确认。

## 3. 如何接入不同的 AI 工具

**不要创建工具专属的规则副本。** 按下表方式让工具读取 `AGENTS.md` 即可：

| 工具形态 | 接入方式 |
|---|---|
| 支持 `AGENTS.md` 约定的工具 | 无需任何配置，自动读取根目录 `AGENTS.md` |
| 支持自定义「项目规则 / 指令」的工具 | 在项目规则中写一行引用：`先阅读并遵守根目录 AGENTS.md` |
| 仅支持会话式交互的工具 | 首次对话时直接说明：「请先阅读 AGENTS.md 并遵守其中规范」 |
| 需要固定入口文件名的工具 | 在**用户级**（非仓库级）配置中指向 `AGENTS.md`，避免污染仓库 |

**判断标准**：如果某个配置文件只对一款产品生效、且需要随产品更新而维护，它就**不应该**出现在本仓库中。此时应改为「引用 `AGENTS.md`」。

## 4. 任务流程中的 AI 职责

| 阶段 | AI 应答 | 人类应答 |
|---|---|---|
| 需求澄清 | 指出歧义与缺失信息，不擅自假定关键需求 | 确认需求边界与优先级 |
| 方案设计 | 给出方案与权衡、影响范围、风险 | 拍板选型 |
| 编码实现 | 遵循规范，写代码同时写测试 | 审查关键逻辑 |
| 自检 | 运行检查与测试，修复自身引入的问题 | 复核结果真实性 |
| 交付 | 说明改了什么、为什么、如何验证 | 验收 |

**关键约束**：AI **不负责最终判断**。安全、鉴权、加密、数据删除、架构变更等高风险改动，必须由人类审查确认。

## 5. 提示词规范

详见 [`PROMPTS.md`](PROMPTS.md)。基本要求：

- **给上下文**：指明相关文档与文件，不要让 AI 猜。
- **给边界**：说明不要做什么（不改哪些文件、不引入依赖、不改接口）。
- **给验收标准**：说明怎样算完成，便于 AI 自检。
- **一次一件事**：任务过大时先让 AI 拆解，再逐项执行。

## 6. AI 输出的质量门禁

AI 生成的任何内容，进入仓库前必须满足：

- [ ] 代码可编译、可运行，**实际验证过**（不是「应该可以」）
- [ ] 有对应的测试，且测试通过
- [ ] 未引入未被确认的新依赖
- [ ] 未臆造不存在的 API、配置项、字段
- [ ] 未包含密钥、令牌、真实数据
- [ ] 符合 `docs/04-engineering/CODING_STANDARDS.md`
- [ ] **无过度设计与过度封装**：没有为假想需求预留的扩展点，没有说不清用途的抽象层、包装器或设计模式
- [ ] **性能与资源无明显退化**：无 N+1 查询、无全量加载、无无界缓存；关键路径有数据支撑
- [ ] 可读性达标：不了解背景的人能读懂主要逻辑
- [ ] 鉴权、加密、数据处理等敏感代码经**人工逐行审查**
- [ ] 相关文档已同步更新

## 7. 风险与边界

### 已知风险

| 风险 | 表现 | 应对 |
|---|---|---|
| 幻觉 | 编造不存在的 API / 库 / 版本 | 要求提供依据；不确定则查证 |
| 过度自信 | 声称「已测试通过」但未真正运行 | 要求给出实际命令与输出 |
| 范围蔓延 | 顺手重构无关代码 | 明确最小改动约束，审查 diff |
| 规范遗忘 | 长会话中偏离规范 | 关键节点重述约束；`AGENTS.md` 常驻上下文 |
| 安全疏漏 | 生成含漏洞的代码 | 敏感代码强制人工审查 |

### 明确边界

AI **不得**在未获人类确认的情况下：

- 修改 `AGENTS.md` 中的红线条款
- 执行破坏性命令（删除、强制推送、清库）
- 引入或升级重要依赖
- 变更对外接口契约
- 修改历史 ADR

## 8. 记录与追溯

- AI 参与的改动，由**提交者**在 PR 描述中说明，责任归属于提交者本人。
- 重大设计由 AI 辅助产出的，应记录 ADR，并在其中注明 AI 参与。
- 不要提交 AI 生成的中间产物（草稿、调试脚本）。
