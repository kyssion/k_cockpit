---

## 使用原则

- **上下文优先**：明确告知相关文档与文件，减少 AI 猜测。
- **边界明确**：指明不能改什么、不能引入什么。
- **验收可测**：给出完成标准，便于 AI 自检。
- **一次一事**：任务过大先拆解。
- **要求举证**：涉及 API、配置、版本时，要求给出依据。

## 1. 会话开场（通用）

```text
请先阅读并遵守仓库根目录的 AGENTS.md，以及以下文档：
- docs/02-architecture/ARCHITECTURE.md
- docs/04-engineering/CODING_STANDARDS.md

当前任务：<一句话描述>

约束：
- 只改动与任务相关的文件，不要顺手重构或格式化无关代码
- 不要引入新的第三方依赖
- 不确定的 API / 配置必须先询问，不要臆造
- 完成后运行 <检查/测试命令> 并报告结果
```

## 2. 需求澄清

```text
我要实现 <功能>，需求见 docs/07-specs/<文件>。

请先不要写代码，先做以下事情：
1. 列出你识别到的歧义点与缺失信息
2. 列出这个需求隐含的边界情况
3. 提出需要我确认的问题（按重要程度排序）

等我确认后再进入设计阶段。
```

---

## 3. 方案设计

```text
基于需求 <链接/描述>，请给出实现方案，包含：
1. 涉及哪些模块与文件，各自的改动点
2. 整体流程与关键数据结构
3. 至少两个可选方案的对比（优势、劣势、维护成本）
4. 潜在风险、性能影响、兼容性影响
5. 测试策略

不要写代码，先让我确认方案。
```

---

## 4. 功能实现

```text
按已确认的方案实现 <功能>。

要求：
- 遵循 AGENTS.md 与 docs/04-engineering/CODING_STANDARDS.md
- 同时编写单元测试，覆盖正常路径、边界值、异常路径
- **不要过度设计、不要过度封装**：只实现当前需求，不添加无人使用的抽象层、包装器、配置项或扩展点
- **注意性能与资源占用**：避免循环内 I/O、全量加载、无界缓存、大对象无谓拷贝
- **保持可读性**：优先选择直接清晰的实现，而非「灵活」的间接层
- 不修改无关文件，不改动既有接口签名
- 涉及数据库/接口变更时，同步更新 docs/02-architecture/DATA_MODEL.md 或 docs/03-api/API.md
- 完成后运行 <命令> 并贴出实际输出

先列出实施步骤（TODO），再逐项执行。
```

## 5. 缺陷修复

```text
现象：<描述>
复现步骤：<步骤>
期望：<期望行为>
实际：<实际行为>
报错信息：<日志/堆栈>

请：
1. 先定位根因（不要直接给修复方案）
2. 说明问题影响的其它调用点
3. 给出最小改动的修复
4. 补充一个能复现该缺陷的回归测试，并确认修复前失败、修复后通过
```

## 6. 代码审查

```text
请审查以下改动（或 git diff）：

重点检查：
- 正确性与边界条件
- 安全隐患（注入、越权、密钥泄漏、SSRF、XSS）
- 错误处理是否完整（有无吞异常）
- 是否引入不必要的复杂度或依赖
- 测试是否充分
- 与 AGENTS.md 及既有约定是否一致

输出格式：按「严重 / 一般 / 建议」分级列出问题，每条给出文件:行号与修改建议。
不要重写整个文件，只指出问题。
```

## 7. 重构

```text
目标：重构 <模块>，改善 <具体问题>。

硬性约束：
- 不改变外部行为与公开接口
- 不改变现有测试的断言预期（除必要的接口调整）
- 分步骤进行，每步保持可运行

请先说明重构步骤与每一步的验证方式，确认后再执行。
```

## 8. 文档生成

```text
请为 <模块/文件> 生成文档，要求：
- 面向 <读者：新人 / 使用者 / 维护者>
- 说明职责、对外接口、依赖、注意事项
- 不描述显而易见的实现细节
- 写入 docs/<对应目录>/，并在 docs/README.md 索引中登记
- 语言与既有文档保持一致

不要修改代码。
```

## 9. 测试补充

```text
请为 <文件/函数> 补充测试，覆盖：
- 正常路径
- 边界值（空值、极值、超长输入）
- 异常路径（依赖失败、权限不足、超时）
- 并发或重复调用场景（若适用）

要求：
- 使用项目既有的测试框架与风格
- 测试相互独立、结果确定，不依赖执行顺序
- 不修改生产代码（若发现需修改，先说明原因）
```

## 10. 任务拆解

```text
请把 <大需求> 拆解为可独立交付并验证的任务，输出：
| 序号 | 任务 | 涉及文件 | 依赖 | 验收标准 | 预估复杂度 |

要求：
- 每个任务应可独立提交，不产生半成品状态
- 标注任务之间的依赖顺序
- 指出哪些任务需要人工审查（安全、数据、架构相关）
```

## 11. 反模式（不要这样提问）

| 反模式 | 问题 | 改进 |
|---|---|---|
| 「帮我优化一下代码」 | 目标不明确，AI 会乱改 | 指明优化目标与指标 |
| 「随便实现个登录」 | 缺失需求，AI 会臆造 | 给需求文档与验收标准 |
| 「你确定这样对吗？」 | 诱导 AI 迎合 | 要求给出依据与反例 |
| 一次塞入 10 个需求 | 上下文混乱，质量下降 | 拆解后逐个处理 |
| 不说技术栈就要求写代码 | AI 只能猜 | 先明确技术栈（或让其询问） |
