# Git 协作流程

> 状态：草稿
> 最后更新：<!-- TODO: YYYY-MM-DD -->

本文档描述与**具体代码托管平台无关**的协作流程。无论使用何种平台，规则一致。

---

## 1. 分支模型

```
main                  # 主分支，始终可发布；禁止直接推送
├── feat/<描述>        # 新功能
├── fix/<描述>         # 缺陷修复
├── docs/<描述>        # 文档变更
├── refactor/<描述>    # 重构（不改变外部行为）
├── perf/<描述>        # 性能优化
├── test/<描述>        # 测试补充
├── chore/<描述>       # 构建、依赖、工具链
└── hotfix/<描述>      # 生产紧急修复
```

**命名规则**：
- 全小写英文 + 连字符，描述控制在 3-5 个单词，例如 `feat/order-export`。
- 包含 Issue 编号（若使用 Issue 跟踪）：`feat/123-order-export`。
- 一分支只做一件事，生命周期尽量短（建议不超过 3 天）。

## 2. 提交信息规范

采用 [Conventional Commits](https://www.conventionalcommits.org/)：

```
<type>(<scope>): <描述>

<正文：说明动机与方案权衡>

<脚注：BREAKING CHANGE / 关联事项>
```

### type 取值

| type | 用途 |
|---|---|
| feat | 新增功能 |
| fix | 缺陷修复 |
| docs | 文档 |
| style | 格式化（不影响逻辑） |
| refactor | 重构（不改变外部行为） |
| perf | 性能优化 |
| test | 测试相关 |
| build | 构建系统或依赖 |
| ci | CI 配置 |
| chore | 杂项（不修改源码与测试） |
| revert | 回滚 |

### 示例

```
feat(auth): 支持手机号验证码登录

fix(api): 修复分页参数越界导致的服务端异常

docs(architecture): 补充缓存层设计说明

refactor(order): 抽取价格计算逻辑便于复用与测试
```

### 规则

- 描述行不超过 72 个字符，使用祈使语气，结尾不加句号。
- 语言全仓库统一（中文或英文，二选一，见 `CONTRIBUTING.md`）。
- **一个提交只做一件事**：禁止把格式化与功能改动混在一个提交里。
- 不兼容变更必须写 `BREAKING CHANGE:` 脚注并说明迁移方式。
- 禁止提交「WIP」「临时提交」这类无意义信息到 `main`。

## 3. 日常流程

```bash
# 1. 同步主干
git switch main
git pull --rebase origin main

# 2. 创建分支
git switch -c feat/your-feature

# 3. 开发并提交（小步提交，信息规范）
git add -p            # 按需选择改动，避免误提交
git commit -m "feat(scope): 描述"

# 4. 保持与主干同步（推荐 rebase，保持历史线性）
git fetch origin
git rebase origin/main

# 5. 推送
git push -u origin feat/your-feature
```

## 4. 合并请求（Pull Request / Merge Request）

### 提交前自检清单

- [ ] 本地格式化与静态检查通过，无新增告警
- [ ] 相关测试通过，新增逻辑有对应测试
- [ ] **无过度设计与过度封装**：没有多余抽象层、包装器、假想扩展点
- [ ] **性能与资源占用无明显退化**：无 N+1、无全量加载、无无界缓存；性能敏感改动有数据支撑
- [ ] 未提交任何密钥、`.env`、真实凭据或生产数据
- [ ] 未提交构建产物或大体积二进制文件
- [ ] 相关文档已同步更新（见 `AGENTS.md` 第 8 节）
- [ ] 提交历史清晰，无「WIP」类提交

### 请求描述必须包含

```markdown
## 变更内容
<!-- 做了什么，涉及哪些模块 -->

## 变更原因
<!-- 为什么要做，关联 Issue / 需求编号 -->

## 实现方案
<!-- 关键设计取舍；若有替代方案，说明为何未采用 -->

## 验证方式
<!-- 如何验证：测试命令、手测步骤、截图或日志 -->

## 影响范围
<!-- 是否影响接口、数据结构、配置、部署方式 -->
- [ ] 需要数据库迁移
- [ ] 需要新增/变更环境变量
- [ ] 存在不兼容变更
- [ ] 需要同步更新文档

## 检查清单
- [ ] 已自测
- [ ] 已补充测试
- [ ] 无敏感信息
```

### 评审要求

- 至少 **1 位** Reviewer 批准；核心模块（见 `docs/06-decisions/` 或负责人约定）需 **2 位**。
- CI 必须全部通过。
- 评审关注：正确性、边界条件、安全性、可维护性、测试充分性、文档一致性。
- 评审意见应具体、可执行；作者必须逐条回应（修改或说明理由）。

### 合并方式

- 采用 **Squash Merge**（或 Rebase Merge），保持 `main` 历史线性可读。
- 合并前确保分支与 `main` 无冲突。
- 合并后删除源分支。

## 5. 冲突处理

```bash
git fetch origin
git rebase origin/main
# 逐个解决冲突
git add <已解决的文件>
git rebase --continue
```

- **禁止**在冲突时直接使用 `--force` 覆盖他人改动。
- 冲突解决后必须**重新运行测试**。
- 涉及他人代码的冲突，应联系原作者确认语义。

---

## 6. 版本发布

- 版本号遵循 [语义化版本](https://semver.org/lang/zh-CN/)：`MAJOR.MINOR.PATCH`。
- 发布时在 `CHANGELOG.md` 记录变更并打标签（tag）。
- 标签命名：`vX.Y.Z`。
- 发布分支上禁止直接修改代码，修复走 `hotfix/`。

---

## 7. 禁止行为（红线）

| 禁止 | 原因 |
|---|---|
| 直接推送 `main` | 绕过评审，破坏可发布性 |
| 强制推送共享分支 | 覆盖他人提交，造成丢失 |
| 强制推送 `main` | 严重破坏仓库历史 |
| 提交密钥或凭据 | 安全事故，且历史难以清除 |
| 提交构建产物 / 大文件 | 污染仓库，拖慢克隆 |
| 绕过 CI（如 `--no-verify`） | 绕过质量门禁 |
| 重写已推送的公共历史 | 破坏协作者的仓库状态 |

> 如需强制推送**自己的功能分支**，使用 `--force-with-lease` 而非 `--force`，并提前告知协作者。

---

## 8. 提交前的本地检查

```bash
# TODO: 技术栈确定后补充实际命令
# 1. 格式化
# 2. 静态检查
# 3. 单元测试
# 4. 快速全量检查
```

建议通过 Git 钩子在提交前自动执行（选型后配置），但**不依赖钩子作为唯一防线**。
