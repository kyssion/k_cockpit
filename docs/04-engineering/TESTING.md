## 1. 测试原则

- **测试是交付物的一部分**，不是可选项。新增业务逻辑必须配套测试。
- **测试行为，不测实现**：断言对外可观察的结果，避免因重构而失效。
- **快速反馈**：单元测试应能在秒级完成，不依赖网络与真实外部服务。
- **确定性**：测试结果可重复，不依赖执行顺序、当前时间、随机结果。
- **一个测试只验证一件事**，失败时能直接定位问题。
- **测试代码与生产代码同等质量**：同样需要清晰命名与适当抽象。

---

## 2. 测试分层

| 层级 | 范围 | 是否依赖外部 | 数量占比 | 执行时机 |
|---|---|---|---|---|
| 单元测试 | 单个函数/类 | 否（全部打桩） | 最多（约 70%） | 每次提交 |
| 集成测试 | 模块间协作、数据库 | 是 | 中等（约 20%） | 每次提交 |
| 端到端测试 | 完整用户链路 | 是 | 最少（约 10%） | 合并前 / 定时 |

**原则**：能用单元测试覆盖的，不要放到端到端；测试金字塔底部要厚。

**前端（`web/`）的层级对应**（规划中）：

| 层级 | 工具 | 覆盖对象 |
|---|---|---|
| 单元 / 组件 | Vitest + React Testing Library（jsdom） | 组件行为、hooks、格式化与工具函数 |
| 集成 | Vitest + MSW（拦截接口） | 页面级数据流：列表渲染、表单提交、错误态与空态 |
| 端到端 | Playwright | 核心用户链路：登录、创建虚拟机、开关机、任务进度 |

## 3. 命名与结构

- 测试文件与被测对象**同目录或镜像目录**存放，<!-- TODO: 确定约定 -->。
- 测试名格式：`被测对象_场景_期望结果`。
- 结构建议采用 **Arrange-Act-Assert**（准备 → 执行 → 断言），三段清晰分隔。
- 断言必须具体：校验**值**而非仅校验「非空」。
- 禁止断言写死当前时间、随机值或环境相关的量。

---

## 4. 必须覆盖的场景

每个功能至少覆盖：

- **正常路径**：典型输入得到预期输出。
- **边界值**：最小值、最大值、空集合、零、超长输入。
- **异常路径**：非法输入、依赖失败、超时、权限不足。
- **幂等/重复调用**（写操作）：重复提交不产生重复数据。

**重点覆盖区域**：金额计算、权限校验、状态机流转、并发与竞态、数据处理边界。

---

## 5. 测试数据

- **禁止**使用真实用户数据或生产数据副本。
- 测试数据必须**脱敏**，或使用构造的假数据。
- 测试数据在测试内**自建自清**，不依赖外部遗留状态。
- 敏感场景（如口令）使用固定假值，不用真实凭据。
- 时间相关逻辑使用**可注入的时间源**，不直接读系统时间。

---

## 6. 测试替身（Mock / Stub）

- 只对外部依赖（网络、数据库、文件系统、时间）做替身。
- **不要**对被测对象自身的方法打桩，否则测试失去意义。
- 优先使用真实实现（如内存数据库）而非替身，以提高可信度。
- 避免过度 mock 导致测试与实现强耦合。

---

## 7. 覆盖率

- 覆盖率是**参考指标，不是目标**。禁止为凑覆盖率写无意义的测试。
- 建议门槛：核心业务逻辑行覆盖 ≥ <!-- TODO: 例如 80% -->，整体 ≥ <!-- TODO -->。
- 覆盖率下降的 PR 需要说明理由。
- **未被覆盖的核心分支视为风险**，需在 PR 描述中标注。

## 8. 运行方式

```bash
# 后端
go test ./...                    # 全部
go test ./internal/handler/...   # 单个包
go test -run TestName ./...      # 按名称筛选
go test -cover ./...             # 覆盖率

# 前端（web/，尚未创建；技术栈见 ADR-0006）
cd web
pnpm test                        # Vitest（追加文件路径可测单个文件）
pnpm test --coverage             # 覆盖率
pnpm test:e2e                    # Playwright E2E
```

---

## 9. CI 中的测试

- 每次推送与 PR 自动运行单元测试与集成测试。
- 测试失败**阻断合并**，不允许跳过。
- 测试必须是**确定性**的；不稳定的测试（flaky）需立即修复或标记隔离，不得直接重试了事。
- 禁止通过跳过测试、注释断言的方式让 CI 变绿。

## E2E 冒烟（Playwright）

**范围**：登录与导航这条「面板从零到能用」的最短链路——初始化（真实走
ADR-0008 的令牌流程，不直插数据库）、登录（含错误密码与首次安全引导的
跳过）、工作台进入、虚拟机列表导航。这些坏掉时用户连备用入口都没有。

**形态**：`pnpm --dir web test:e2e` 一条命令自拉自拆——Playwright 的双
webServer 先起一个**独立控制面**（临时 SQLite、`AGENT_TRANSPORT=mock`、
`cmd/e2e-init` 按模型建全套表——SQL 迁移是 PG 专用的，冒烟栈不走它），
再起 vite（`KC_API_TARGET` 指向冒烟控制面）。每次运行都是干净库，
与本机开发并行不互踩（端口 8099 / 5179）。

**边界**：创建 / 电源 / 控制台 / 迁移等核心链路的端到端覆盖依赖真实
agent 的行为（mock 下测的是假成功），按 M5 验收批次的口径补全量用例。

## 性能压测的口径（M4 非功能需求的处理决定）

**压测延后到真实 agent 落地之后**，且在此之前不做任何"替代性"的压测。
理由不是省事，而是测了会骗人：

- 控制面当前的主要耗时都在 **mock agent 的内存调用**上——真实链路里
  libvirt / OVS / 存储操作的耗时（迁移复制、磁盘制备、快照合并）在 mock
  里全部为零。此刻压出来的任何 P95 数字都只反映"数据库 + 序列化"的
  开销，拿它当容量依据会严重高估系统能力；
- 反过来，任务队列、调度器、实时通道这些**纯控制面**的并发面已经由
  单元测试与 CI 覆盖行为正确性；它们在真实部署里的容量瓶颈（如任务
  积压上限）需要真实任务耗时才有意义。

真实 agent 落地后的首轮压测范围（到时按此立项）：创建 / 电源 / 迁移
三类任务在 10 / 50 并发下的吞吐与 P95、SSE 实时通道在 100 并发订阅下
的内存与延迟、列表页在 5000 台虚拟机规模下的查询耗时。

## 可观测性的口径

控制面**不自建指标导出端点**（Prometheus / OTel 一类）直到真实 agent
落地：数据面的关键指标（CPU / 内存 / 磁盘 IO / 网络）本来就来自节点，
没有真实节点时这些序列全是 mock 常量，导出它们只会污染使用方的图表。

现有的可观测落点维持不变：结构化日志（脱敏 + gzip 归档）、请求日志
（按需开启）、审计流水、调度事件、`GET /health`。外部指标接入随 agent
的遥测通道一并设计（届时新建 ADR）。
