## 1. 交付目标与判定口径

**目标**：测试完成后，系统可在生产形态（PostgreSQL + Linux 控制面 + 真实 KVM 节点 agent）下管理真实宿主机，且无已知的阻断级缺陷。

**交付 ≠ 零缺陷**。判定分三档，必须在 §8 的报告中逐项落名：

| 档 | 含义 | 处理 |
|---|---|---|
| **A 阻断交付** | 数据丢失 / 越权 / 假成功 / 控制面崩溃 / 节点失联 / 无法从零安装 | 必须修复并全量回归，不得豁免 |
| **B 有记录的边界** | 架构决策明确不做、或需先新建 ADR / 双机环境的能力（如 live 热迁移、外部身份源） | 列入 §9 豁免单，文档与界面必须**诚实阻断**且不出现假成功，经确认后可交付 |
| **C 延后项** | 不影响主流程的打磨项（如 agent 遥测、外部指标接入） | 记录到 `ROADMAP.md`，不占本次出口门槛 |

**「诚实阻断」是硬要求**：B 档能力若界面显示可用、点下去才失败或返回成功但什么都没做，一律升为 A 档。

### 3.2 证据的边界（不能据此宣称可交付）

1. **环境是 SQLite 单节点**：r8 ~ r13 全在 macOS 控制面 + SQLite `data/lab2/kc.db` + 单台 KVM 节点上跑。生产形态的 **PostgreSQL 迁移、单实例锁、PG 专用 SQL 迁移均未验**（`AGENT_ACCEPTANCE.md` §1 第 2 条）。`TESTING.md` 已注明冒烟栈用 `cmd/e2e-init` 按模型建表、不走 PG 专用迁移。
2. **前端 E2E 只有冒烟档进 CI**：R1 只覆盖登录与导航；创建 / 电源 / 控制台 / 迁移核心链路无浏览器级自动证据。R2 的 38 路由只断言「可加载且无 5xx」，**不能等价于功能验收**。
3. **文档状态滞后于实测**：`ROADMAP.md` §5.2 六项、`SECURITY_REVIEW.md` §3 三项、`AGENT_ACCEPTANCE.md` 全部勾选项、`f-6-08-agent.md` 的「真机待验」均仍是未勾选；其中一部分其实已有 r8~r13 的证据，但**未回填、也未逐条判定**。本次必须先做「证据 ↔ 清单」对账（TP-23），再决定补测哪些。
4. **五项硬缺口无证据**：双机迁移 / relay、压测、外部可观测性、agent 侧日志与遥测、发布与回滚（`AGENT_ACCEPTANCE.md` §8、`ROADMAP.md` §5.2/5.3）。
5. **`AGENT_ACCEPTANCE.md` §3 的 37 项「单测通过、真机待验」**：r12/r13 补测了其中大部分写路径，但**没有一份逐项对照表**说明哪 37 项各自在哪个套件里被验过。本次必须补出该表（§6.4）。
6. **真机测试资产未随代码交付**：`data/` 被 `.gitignore` 忽略（报告不入库），26 套 Python 套件位于仓库外的 `~/.kc_test/`。干净检出上只有 R1 能复跑，**R2/R3 的编排、脚本、环境前提、日志路径都不在交付物里**（G-13）。
7. **Go 侧无 HTTP 路由级用例**：227 个 Go 测试文件全是单包行为测试；`internal/router/` 下 3 个 `_test.go` 只测 SPA 静态回退、路由覆盖与 fallback，**没有任何一条业务路由的 401/403/428/参数绑定/状态码契约测试**；`internal/service/` 下 `search`、`authkey`、`mailer`、`passaudit`、`reqlog`、`reconcile` 等子包零测试文件。HTTP 面目前完全依赖 R3 的 Python 套件（G-14）。
8. **契约清单不完整且无自动对账**：`API.md` 289 行登记未逐条覆盖 340 条运行时域路由；`endpoints.json` 的 auth 字段是 r13 修复前旧值；`reference/` 内无 `images` 相关路由，导入真实入口是 `/api/v1/imports/*` 六条（G-15）。
9. **前端构建产物同步未验**：`web/dist` 需拷入控制面 `STATIC_DIR`（默认 `public`）才算真正托管，该步骤未纳入任何门禁（G-16）。

### 3.3 回归必须自带的环境复位（r13 §4 的教训）

- 回归脚本开头重建 `/dev/nbd3` 测试盘（`t_r12_storage_b.py` 结束会断开并删除镜像）；
- 节点重启会同时丢 nbd 挂载、iptables DNAT、VM 开机状态、VNC 开关，并在 OVS 留下 `vnet*` 幽灵端口；回归前复位：`virsh start` 两台基准 VM、`ovs-vsctl del-port` 清幽灵端口、重开控制台、清历史转发与 DNAT；
- 测试库 `system_setting` 存在历史显式覆盖 `vm.stale_threshold_seconds=60`，验证默认行为前需清除；
- 新用户首次登录触发 `force_password_change`，脚本必须用登录后的实际密码；
- `DELETE /vms/:id` 必带 `?disk_action=delete|keep|transfer`；
- `t_final.py` 的环境性 503 白名单只含「邮件未配置三接口」与「故障注入期间节点离线的存量域扫描」，**放宽判定口径必须保留「真 5xx 仍判失败」的方向**；
- 控制台 WS 被浏览器 RST 后第三方库内部 panic 已由 `pipeConsole` 双协程 `recover` 兜住，白名单只排除这一条带标注的记录。

2. **边界**：空集合 / 0 / 最大值 / 超长 / Unicode / 枚举外值；

4. **幂等与并发**：重复提交、同名并发、批量部分失败；

6. **审计**：写操作留痕、敏感字段脱敏、前后态；
7. **节点事实**：按 `AGENT_ACCEPTANCE.md` §0 四条判定；
8. **失败回滚**：不留孤儿域 / 半截文件 / 悬空规则 / 卡在 `running` 的任务。

### 6.8 完整性校验的机械方法（防止「人眼看着齐了」）

每次计划重跑前执行**四份**对账，输出 orphan 列表并归档到测试报告：

1. **路由对账**：脚本从 `internal/router/routes_*.go` 抽 `METHOD + PATH`（**唯一权威**，342 个实际端点）→ 与 `API.md` §5 登记行、`internal/handler/platform/apidocs_meta.go` 的 `adminAPIRoutes` / `publicAPIRoutes`、`web/src/api/` 的调用、`/api-endpoints` 清单（341 条）比对；同时输出 160 条 `adminOnly` 的守卫分层矩阵，并**双向反查**：`adminOnly` 接口 → 前端调用点 → 所属页面 → 该页面/菜单的角色可见性（抓 G-20 的页面内落差），以及「后端有、前端未用」的孤儿接口（由对账产出，不预设具体端点）。**注意 `/tasks/clear` 不是孤儿接口**（`TaskListPage.tsx:593` 有调用点，属 G-20 页面内落差）；`GET /vms/:id/public-ips/guest-status` 不属于 `/public-ips` 组且仅 `requireAuth`，不得按组判为 403；
2. **能力对账**：从 `internal/agent/agent.go` 的 `OpKind` 常量 + `internal/nodeagent` 注册表引用抽能力清单（131 项）→ 与「节点能力页实际返回」、`AGENT_ACCEPTANCE.md` §3 的 37 项表、本文 §6.4 对照；
3. **矩阵对账**：从 `PRD.md` §4.1 抽 94 个 `F-x-xx` → 与本文 §6.1 的键集合比对；从 `web/src/router/index.tsx` 抽 46 条 path → 与 TP-16 用例清单、`web/e2e-live/live.spec.ts` 的 38 条 `ROUTES` 比对；

任一侧出现「有实现无用例」或「有用例无实现」，都必须在报告中给出结论，不允许静默忽略。统计范围明确排除 `reference/kite/`（只读参考子模块）、`node_modules/`、`dist/`、`build/`；`data/` 与 `/public/` 不入库，属 R3/制品范畴。
