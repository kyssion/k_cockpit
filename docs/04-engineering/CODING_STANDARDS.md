# 编码规范

> 状态：草稿

## 1. 基本原则

- **可读性优先**：代码被阅读的次数远多于被编写的次数。可读性优先于「优雅」「聪明」与「灵活」。
- **克制设计**：只解决当前问题。不过度设计，不过度封装（见第 2、3 节）。
- **显式优于隐式**：不依赖魔法行为、隐式转换、副作用。
- **简单优于复杂**：能被直接读懂的代码，好过需要绕几层才明白的「灵活」结构。
- **一致性**：与既有代码风格保持一致，即使你个人有别的偏好。
- **最小改动**：修改现有代码时，不做与任务无关的重构与格式化。

**总体判断标准**：如果一段代码删掉后功能不受任何影响，那它就是多余的。

## 2. 避免过度设计

### 2.1 核心原则：YAGNI

只为**当前明确的需求**设计。

- **禁止为假想需求预留**：不预留「以后可能要用」的扩展点、钩子函数、插件机制、配置开关。
- **禁止实现用不到的功能**：未被需求文档或规格确认的能力，不提前实现。
- **禁止为不存在的场景写分支**：不确定的错误情况用明确的方式处理，不写「防御性」的空分支。
- **禁止通用化冲动**：只有一个调用点时，不要把它抽象成「通用框架」。
- **禁止过度分层**：层数必须与问题的真实复杂度匹配。一个 CRUD 功能不需要领域层 + 服务层 + 仓储层 + 工厂层。

### 2.2 例外情况

只有在**同时满足**以下条件时，才允许适度预留：

1. 有明确的需求依据（PRD、规格或 Issue 中已列出的近期计划）；
2. 预留的成本极低，且不增加理解负担。

此时必须在代码注释中说明依据，例如：`// 预留：F-00X 需求将在下个迭代接入`。

### 2.3 自检问题

提交前问自己：

- 这段抽象现在有**两个以上**真实使用场景吗？
- 为什么这样设计？**能说清解决的具体问题吗**？
- 如果把这段代码删掉，当前功能会受影响吗？

答不上来就是过度设计。

## 3. 避免过度封装

### 3.1 禁止的行为

- **无意义包装**：只做转发、不做任何加工的 wrapper（如 `getUser() { return this.userRepo.findUser(); }`）。
- **抽象层泛滥**：Manager / Helper / Util / Factory / Handler 逐个堆叠，层层转发，实际问题却没变复杂。
- **为「灵活」暴露接口**：把内部细节暴露出去只为「万一以后要扩展」。
- **设计模式堆砌**：设计模式是解决特定问题的工具，不为用而用。用了却说不清解决什么问题，就是过度设计。
- **过早抽象**：在只有一处重复时提取「通用组件」，导致参数膨胀、分支蔓延，比重复代码更难维护。

### 3.2 抽象的正确时机

遵循**三次法则**（Rule of Three）：

| 重复次数 | 处理方式 |
|---|---|
| 1 次 | 直接写，不要抽象 |
| 2 次 | 可以容忍重复，观察是否稳定 |
| 3 次及以上 | 且形态稳定，才提取抽象 |

**关键**：抽象必须让代码**更简单**。如果抽象后的调用方需要传更多参数、写更多分支才能用，那它失败了。

### 3.3 封装的分寸

- 该封装的：**变化点**、**外部依赖**、**复杂算法**、**重复出现的业务规则**。
- 不该封装的：一次性逻辑、纯数据传递、没有变化的简单调用。
- 封装后应**隐藏复杂度**，而不是**转移复杂度**给调用方。
- 模块对外接口应保持最小，只暴露必要能力。

## 4. 性能与资源占用

### 4.1 时间开销

- **避免 N+1**：禁止在循环内做数据库查询、网络请求、文件读写。批量操作用批量接口。
- **避免重复计算**：循环外可算的量不要放进循环；不变的表达式提到循环外。
- **选择合适的数据结构**：按访问模式选择；避免在高频查找场景使用线性结构。
- **合理使用并发**：相互独立的 I/O 操作可并发执行，但不要为并发而并发——并发会带来复杂度与资源开销。
- **避免不必要的序列化/拷贝**：大对象在层间反复转换与拷贝是常见性能陷阱。

### 4.2 空间与资源

- **避免全量加载**：大数据集必须分页、流式或分批处理，不要把整表读进内存。
- **缓存必须有界**：所有缓存必须设置容量上限与失效策略（TTL / LRU），**禁止无界缓存**。
- **及时释放资源**：文件句柄、连接、锁、订阅必须在作用域结束时释放，优先使用语言提供的确定性释放机制。
- **连接复用**：数据库与 HTTP 连接使用连接池，禁止每次请求新建连接。
- **注意内存驻留**：避免长时间持有大对象引用；避免在集合中长期累积数据。
- **关注启动开销**：避免在启动路径做耗时操作或加载不必要的数据。

### 4.3 优化原则

- **先测量，再优化**：不做没有数据支撑的优化。猜测的性能瓶颈通常是错的。
- **不做过早优化**：清晰正确的实现优先；在证明是瓶颈后再优化。
- **也不主动写低效代码**：「不提前优化」不是写出明显低效实现的借口。N+1 查询、全表扫描、无界缓存属于**缺陷**，不是「未优化」。
- **优化必须可验证**：优化前后要有基准数据对比，并在 PR 中说明。

### 4.4 性能敏感路径的要求

- 明确标注哪些是性能敏感路径（高频调用、大数据量、用户等待链路）。
- 敏感路径需有基准测试或压测数据。
- 敏感路径的改动，PR 中必须给出性能影响说明。

## 5. 命名

| 对象 | 约定 |
|---|---|
| 变量/函数 | 见名知意，使用完整单词，避免无意义缩写 |
| 布尔 | 以 `is` / `has` / `can` / `should` 开头 |
| 常量 | 全大写 + 分隔符，或语言惯用形式 |
| 类型/类 | 名词，PascalCase（按语言惯例） |
| 函数 | 动词开头，描述动作 |
| 集合 | 复数形式 |

**禁止**：`data`、`info`、`temp`、`obj`、`list`、`a1`、`tmp2` 这类无信息量的命名；单字母变量仅允许用于简短循环索引与数学推导。

## 6. 函数与模块

- **单一职责**：一个函数只做一件事，能用一句话描述清楚。
- **长度控制**：函数建议不超过 50 行；超过时优先拆分。
- **参数控制**：参数建议不超过 4 个；更多时考虑引入参数对象。
- **嵌套控制**：嵌套不超过 3 层，优先使用**早返回**降低嵌套：

```
// 推荐
if (!valid) return error;
if (!exists) return notFound;
// 主逻辑

// 避免
if (valid) {
  if (exists) {
    // 主逻辑
  }
}
```

- **副作用**：函数名应体现副作用（如 `update`、`delete`），纯计算函数不要有副作用。
- **避免输出参数**：通过返回值传递结果，而非修改入参。
- **不做无谓拆分**：拆分是为了降低理解成本，不是为了「每个函数都很短」。为凑长度把逻辑切碎成难以追踪的碎片，同样损害可读性。

## 7. 注释与文档

- 注释解释 **为什么**（背景、权衡、坑），不解释 **做了什么**。
- 公共 API（导出的函数、类、接口）必须有文档注释，说明**参数、返回值、可能抛出的异常、副作用**。
- 复杂算法/正则/位运算必须注明来源或原理。
- 禁止保留大段注释掉的代码（历史交给版本控制）。
- 禁止无意义注释（如 `// 设置 x 为 1`）。
- `TODO` / `FIXME` 必须带责任人与关联事项，格式：`// TODO(name): 说明`。

## 8. 错误处理

- **禁止吞异常**：空 `catch`、忽略返回值、只打日志不处理，均不可接受。
- 异常信息要包含足够上下文（操作、关键参数），但**不得包含敏感数据**。
- 区分两类错误：
  - **可预期错误**（参数非法、资源不存在）→ 返回明确错误，不中断程序。
  - **程序缺陷**（不变量被破坏）→ 快速失败，暴露问题。
- 资源获取必须配对释放（文件、连接、锁），使用语言提供的确定性释放机制。
- 不使用异常做流程控制。

## 9. 安全编码

- **所有外部输入必须校验**：类型、长度、范围、格式、枚举白名单。
- **SQL**：一律参数化查询，禁止字符串拼接。
- **命令执行**：禁止拼接用户输入；如需执行，使用白名单参数传递。
- **路径**：校验并规范化，防止路径穿越。
- **SSRF**：用户可控 URL 必须白名单校验协议与域名。
- **XSS**：按输出上下文转义，谨慎使用动态 HTML 注入。
- **鉴权**：数据访问必须校验归属与权限，不能仅依赖前端隐藏。
- **加密**：使用成熟库的标准算法，禁止自创算法；口令存储用带盐的慢哈希。
- **日志**：禁止记录口令、令牌、证件号、银行卡号等敏感信息。
- **随机数**：安全场景使用密码学安全随机源，不用普通随机函数。

---

## 10. 依赖管理

- 引入依赖前评估：维护活跃度、体积、协议、已知漏洞、维护者数量。
- 优先使用标准库与已有依赖，避免功能重叠。
- 锁定文件提交到仓库，保证构建可复现。
- 定期执行依赖漏洞扫描。

## 11. 语言专项规范

> 技术栈确定后在此追加，每种语言一节。

### 11.1 Go

- **缩进**：制表符（Tab），由 `gofmt` 强制保证
- **行宽**：见 `.editorconfig`（建议 120，不做硬性限制）
- **格式化**：提交前执行 `gofmt -w .`；CI 通过 `gofmt -l .` 校验（有输出即失败）
- **静态检查**：`go vet ./...`

**命名**

- 包名：全小写、单单词、无下划线（`config`、`database`、`handler`）
- 导出标识符 `PascalCase`；非导出 `camelCase`
- 首字母缩写大小写保持一致：`URL`、`ID`、`HTTP`（不写 `Url`、`Id`、`Http`）
- 接口名：单方法接口用动词 + `er`（`Reader`、`Closer`）；不用 `I` 前缀
- 测试函数：`TestXxx` 或 `TestXxx_场景描述`

**错误处理**

- `if err != nil` 紧跟调用，不延迟判断
- 用 `%w` 包装错误以保留错误链，便于 `errors.Is` / `errors.As` 判断
- 错误信息小写开头、不加标点、不重复函数名，例如 `fmt.Errorf("查询用户失败: %w", err)`
- 错误信息不得泄漏敏感数据；面向客户端的响应只给通用提示，细节记日志

**惯用法**

- 接收者用 1-2 字符短名，同类型保持一致；不用 `this` / `self`
- 切片用 `make` 预分配已知容量；判空用 `len(s) == 0`
- `context.Context` 作为函数首个参数传递；**不把它存进结构体**
- 依赖通过构造函数注入（见 `handler.NewUser`），不用全局变量
- 仅在程序无法继续初始化时使用 `panic`，常规错误一律返回 `error`

**禁忌**

- 不用下划线命名变量或函数（测试文件名除外）
- 不忽略错误；确需忽略时必须显式写明理由
- 不在循环中使用 `defer`（资源会累积到函数结束才释放）
- 不编写 `Get` 前缀的 getter（`user.Name()` 而非 `user.GetName()`）

## 12. AI 生成代码的额外要求

- AI 生成的**鉴权、加密、序列化、文件上传、SQL 拼接**相关代码，必须人工逐行审查后才可提交。
- 不得让 AI 自创安全算法或协议，必须使用成熟库的标准实现。
- AI 声称「应该可以运行」不算验证；**必须实际编译/运行并通过测试**。
- AI 不得臆造不存在的 API 或配置项，不确定时应查询文档或询问。
- **AI 有过度设计倾向**：默认会生成「更通用、更灵活」的结构。因此 AI 生成的设计必须**主动对照第 2、3 节自检**，剥离无人使用的抽象、参数与扩展点后再提交。
- **AI 有忽视性能的倾向**：需主动检查是否存在循环内 I/O、全量加载、无界缓存等问题。
- 使用 AI 生成的代码，责任归属于**提交者本人**。
