# 排障与运维规范

> 状态：生效
> 最后更新：2026-09-13
> 关联：[`../../AGENTS.md`](../../AGENTS.md) · [`DEVELOPMENT.md`](DEVELOPMENT.md) · [`TESTING.md`](TESTING.md) · [`../08-reference/qvmconsole/pitfalls.md`](../08-reference/qvmconsole/pitfalls.md)

本文约定**排查问题**与**操作运行环境**的方法和纪律，适用于本地、远端开发机与宿主机。

目标：**用最短路径定位根因，并且不把环境越改越乱。**

---

## 1. 六条原则

| 原则 | 含义 |
|---|---|
| **先诊断，后动手** | 未收集到足够证据前不修改任何东西。禁止"猜一个改一个"式排查 |
| **定界优先** | 先判断问题属于「环境/依赖」还是「代码」，再决定往下查的方向（见 §2） |
| **证据驱动** | 结论必须能指向具体日志行、文件、命令输出。不接受"应该是……" |
| **最小变更** | 只改与问题直接相关的最小面，不做顺手的重构或"优化" |
| **可回滚** | 每步变更前都想清楚怎么退回去；优先追加式改动，避免覆盖系统原有内容 |
| **留记录** | 改了什么、为什么、怎么验证、有什么遗留影响，都要写清楚并同步进文档 |

---

## 2. 定界：先分清「环境问题」还是「代码问题」

对接宿主机能力的系统（虚拟化、网络、存储、systemd 等），**相当一部分"程序 bug"其实是环境差异**。因此：

1. **为每个依赖外部系统的能力配套实机自检入口**（脚本或 CLI 子命令），真实创建/操作一次资源并校验结果。
2. 自检必须**按阶段输出结论**（`passed` / `failed` / `skipped`），失败时直接告诉人"卡在哪一步"，而不是抛一个笼统错误。
3. 失败信息要给出**可执行的修复方向**（缺哪个命令、装哪个包、改哪个配置）。
4. 新增此类模块时，自检入口与模块同期交付，并在文档登记。

> **参考做法**：QVMConsole 的 `scripts/check-system-compatibility.sh` 会真实创建一台 1vCPU / 1GB / 1GB 磁盘的临时虚拟机，验证 `libvirt → OVS 网桥 → DHCP → NAT → 端口安全` 全链路，无论成败都清理本次唯一命名的资源，并输出 JSON 报告与诊断日志。详见 [`../08-reference/qvmconsole/README.md`](../08-reference/qvmconsole/README.md) §4.5。
>
> **本次收益**：一次现场排障中，正是靠它的报告里"失败阶段"一行，几秒钟锁定了问题范围，而不是从几十行日志里逐条读。

## 3. 远端排障的操作纪律

1. **只读优先**：先收集状态——服务状态、日志、配置文件、端口占用、目录与权限。收集完再判断，不要边猜边改。
2. **记录改前状态**：改配置前先把原文件内容/原规则记下来（或直接备份），否则出问题无法回退。
3. **优先追加式变更**，避免直接修改系统或程序管理的文件：
   - systemd：用 `*.service.d/override.conf` 做 drop-in，**不要改 unit 主文件**（程序可能用模板重写主文件，你的修改会被悄悄抹掉）。
   - 配置文件：改动包在明确的 `# BEGIN ... / # END ...` 标记块里，便于整体回滚且不覆盖他人内容。
4. **变更后立刻验证并说明**：服务状态 + 业务侧真实验证（不是只看进程活着）+ 遗留影响（例如"下次重启还会不会复现"）。
5. **凭据不进文档、不进提交**：排查记录里用泛称（"目标宿主机"、"该服务"），不要写真实 IP、账号、密码、密钥。真实凭据只存在于本地 `.env` 或密钥管理工具中。

## 4. 跨层工具陷阱（实战踩过的）

在「本地 shell → SSH → 远端 shell → 子进程」这种多层环境下，最容易出的不是逻辑错，而是**转义与引号被某一层提前解释**。

| 陷阱 | 现象 | 对策 |
|---|---|---|
| **变量被本地 shell 先展开** | 用 PowerShell 下发远端命令时写了 `$VAR`，被 PowerShell 当成自己的变量展开成空串，远端实际执行 `/kvm-console` 这类错误路径 → 服务报 `status=203/EXEC` | 远端命令**避免使用变量**，直接写绝对路径；必须用时用单引号包裹远端脚本，并先 `echo` 验证展开结果 |
| **引号跨层冲突** | 本地双引号、远端单引号、正则里的引号互相吃掉，命令被截断 | 逐层确认引号归属；复杂脚本改为"本地生成脚本文件 → 上传 → 远端执行" |
| **非交互登录** | 标准 `ssh` 客户端无法自动输入密码，命令挂起或反复失败 | 用支持凭据的客户端（如 PowerShell 的 `Posh-SSH`），或（更推荐）配置密钥 + `sudo` 免密；不要在命令行明文传密码 |
| **`sudo -S` 与 stdin 冲突** | `sudo -S` 会消费 stdin 的第一行（密码），导致后续交互式输入错位 | 先 `sudo -v` 预热会话，或把密码输入与业务输入严格分开；能免密就免密 |
| **长输出被工具折叠** | 只看到摘要/省略号，误判为"没有输出" | 显式展开（join 成整段/分段落获取），或分批只取需要的片段 |
| **远端命令静默截断** | 一次下发过长命令，超出限制后被截断，只执行了前半段 | 拆分命令；或改用脚本文件方式执行 |

## 5. 系统服务类问题检查清单（systemd）

1. `systemctl status <unit>`：重点看 `Loaded` / `Active` / `Result` / `Main PID` 的退出码（`status=0/SUCCESS` 与"服务已结束"是两回事）。
2. `journalctl -u <unit> -n 100 --no-pager`：**看最早的那条错误，而不是最后一条**——最后一条往往是连锁结果。
3. 确认 `Type=` 的含义：
   - `simple`：主进程必须一直前台运行；
   - `forking`：进程必须真正 daemon 化，且 `PIDFile=` 必须真实被写出（配置里写了 `pid-file` 不等于服务会按预期工作）；
   - `notify`：程序必须主动发 readiness 通知。
4. **区分三种"重启"来源**（这是最容易误判的一步）：
   - 服务自己的 `Restart=` 策略触发；
   - 被别的脚本/服务反复 `systemctl start|restart`；
   - **被其他进程直接 kill**。
   > 判定技巧：日志里**没有 `Stopping ...` 记录**就高度怀疑是"外部直接 kill 了进程"，而不是 systemd 在重启它。
5. 出现 `start-limit-hit`：说明短时间重启次数超过 `DefaultStartLimitBurst`（默认 5 次 / 10 秒），systemd 主动熔断。
6. 处置顺序：`systemctl reset-failed <unit>` → 手动 `start` 并观察是否稳定 → 再决定是"修根因"还是"加缓解"。
7. 缓解手段（不改主文件）：加 drop-in
   ```ini
   # /etc/systemd/system/<unit>.d/override.conf
   [Unit]
   StartLimitIntervalSec=0
   [Service]
   Restart=always
   RestartSec=2
   ```
   这能保证"进程被误杀后自动恢复"，但**这只是止痛**，根因仍要修。

## 6. 案例复盘：OVS dnsmasq 被反复误杀 → `start-limit-hit`

> 场景：在目标宿主机上安装并启动一个基于 KVM/libvirt/OVS 的虚拟机管理面板。**文中不记录任何真实主机信息与凭据。**

### 6.1 现象（三层，容易只看最后一层）

1. 表层：`kvm-console-ovs-dnsmasq.service` 处于 `failed`，原因是 `start-limit-hit`。
2. 中层：安装目录里**缺少程序二进制、前端产物和 `.env`**，主服务 unit 甚至不存在。
3. 深层：该次安装的兼容性实机测试报告显示——**失败阶段是"虚拟机已启动，但绑定基础 OVS 网络失败"**。

### 6.2 关键证据

- dnsmasq 每次都能**成功启动**（绑定网桥、读 DHCP 静态绑定、写租约文件），但 **1–2 秒后收到 SIGTERM 退出**，且日志里**没有 systemd 的 `Stopping ...` 记录** → 判定为**外部进程直接 kill**。
- 反复"起→被杀"在 10 秒内达到 5 次 → 触发 systemd 熔断。
- 兼容性测试在"绑定基础 OVS 网络"阶段调用"确保 OVS 网络就绪"，该动作内部启停 dnsmasq。

### 6.3 根因

程序的"确保 OVS 网络就绪"逻辑里有一段"释放 53 端口"的处理：它用 **OVS 自身的网关 IP** 去 `ss -tlnp | grep '<ip>:53'` 查出 PID 然后 `kill`。但 OVS 的 dnsmasq 监听的**正是这个网关地址**，于是它**把自己杀了**；该逻辑在一次流程中会被执行多次，短时间多次"杀掉→拉起"最终触发 systemd 限流。

> 值得记录的是：这个坑上游**修过两次**（先记录"端口被占用"、再提交"精确杀死 libvirt dnsmasq，避免误杀 OVS dnsmasq"），但直到本次实测仍未修到根因——因为**按监听地址判断进程归属本身就是错的**。

### 6.4 处置（按纪律执行）

1. **只读诊断**：收集 unit 内容、dnsmasq 配置、端口占用、`journalctl` 全文、安装目录、测试报告，先不动任何东西。
2. **验证假设**：`systemctl reset-failed` + 手动 `start` + 观察 8 秒 → 确认"单次启动是稳定的，问题来自反复被杀"。
3. **加缓解**（不改会被程序重写的 unit 主文件）：用 drop-in 关闭启动限流并允许自动重启（见 §5.7）。
4. **补齐缺失的部署**：手动完成程序文件、前端产物、最小 `.env`（生成随机密钥）、systemd unit 的部署。
5. **端到端验证**：重跑实机自检脚本 → 通过；再验证页面可访问、默认账号可登录。
6. **记录并沉淀**：把根因写入参考项目文档（含缓解方案），把可复用经验写进本文。

### 6.5 本次得到的结论

1. **"没有 `Stopping` 记录"是判断外部 kill 的关键线索**，比猜测"systemd 在重启它"高效得多。
2. **报错链要往上游找第一条异常**：安装器"撤回程序文件"是设计好的行为，不是故障；真正的第一个异常是网络绑定失败，再往上游才是 dnsmasq 被杀。
3. **"杀掉占用端口的进程"必须有归属校验**（PID 文件 / systemd unit / 进程名 + 参数指纹），**绝不能只凭"监听地址"判断这是别人的进程**。
4. **修 bug 要修到根因**：同一个问题被修两次仍在复现，说明每次都在治标。
5. **缓解手段要选不被覆盖的形式**：程序会重写的 unit 主文件不要手改，用 drop-in。
6. **业务验证不可省**：服务 `active` 不等于功能可用，必须跑一次真实的资源创建链路。

## 7. 运行环境变更清单

**动手前：**

- [ ] 已完成只读诊断，能说清根因或至少能说清疑点
- [ ] 已确认影响面（会影响哪些服务、是否影响下次重启、是否影响已有数据）
- [ ] 已记录/备份原状态，并确认回滚方法
- [ ] 变更范围最小，且不与程序自动生成的配置冲突

**改完后：**

- [ ] 服务状态正常（`systemctl is-active` / `is-enabled`）
- [ ] **业务侧真实验证通过**（创建一次真实资源，而不是只看进程）
- [ ] 遗留影响已说明（哪些场景下问题仍会出现、如何观察）
- [ ] 变更点、回滚方式已写入文档
- [ ] 临时文件与中间产物已清理
