## 1. 背景与目标

### 1.1 背景

多个能力的操作可能耗时数秒到数十分钟（创建、克隆、迁移、重装、导入）。异步化有三个不可回避的理由：

1. **HTTP 超时**：同步等待会让请求超时、重试不可控；
2. **可观测性**：长流程必须能看到「进行到哪一步、为什么失败」；
3. **安全与一致性**：同一资源被并发操作会产生状态错乱。

### 1.2 目标

- 重操作**统一入队**，接口只返回任务标识；
- **同一资源互斥**，影响面大的操作全局串行；
- 任务的**进度、阶段、结果、错误**可查、可取消；
- 控制面与前端之间建立**实时通道**，状态变化可推送而非轮询；
- **节点离线时任务结论未知而非失败**——不得凭失联判定业务失败。

### 1.3 不做什么（范围外）

| 不做 | 归属 |
|---|---|
| 周期性调度器框架、定时任务 | F-7-04（P1）、F-7-05（P2），M3/M4 |
| 各长流程的**具体**失败点与回滚清单 | F-7-06（P1）——本规格只提供**声明机制**（§3.3 R-012） |
| 指标采集与聚合（数据来源） | F-8-01（agent 侧采集）——本规格只负责把已聚合的值推送到前端 |
| 消息中间件（MQ） | 见 §9 Q-001 |

## 3. 功能描述

### 3.1 任务生命周期

```text
pending（已入队，等待资源锁）
  → running（已下发 agent，执行中）
  → success / failed / canceled（终态）
  ↘ unknown（执行中节点失联 → 结果未知，等待重连对账收敛）
```

**状态说明**（与 `task.status` 一致）：

| 状态 | 含义 | 是否终态 |
|---|---|---|
| `pending` | 已入队，等待资源锁或前序任务 | 否 |
| `running` | 已下发给 agent，执行中 | 否 |
| `unknown` | 执行中节点失联，**结果未知**；由重连对账收敛 | 否 |
| `success` | 成功 | 是 |
| `failed` | 失败（附阶段与原因） | 是 |
| `canceled` | 已取消（**不算失败**） | 是 |

### 3.2 交互细节

| 步骤 | 用户操作 | 系统响应 |
|---|---|---|
| 1 | 触发重操作（如创建 VM） | 接口**立即返回任务标识**；界面在任务栏出现进度项 |
| 2 | — | 任务进度经**实时通道**逐阶段推送；阶段名与失败原因可见 |
| 3 | 点击任务项 | 进入任务详情：参数（脱敏）、阶段时间线、结果或失败原因 |
| 4 | 取消 | 二次确认；`pending` 直接取消，`running` 下发取消信号并提示「已完成步骤可能不会回滚」 |
| 5 | 任务终态 | 推送终态事件，界面给出成功 / 失败 / 已取消的**明确结论** |
| 6 | 清理 | 按条件清理已完成任务（终态且超过保留期者可批量清理） |

### 3.3 业务规则

| 编号 | 规则 |
|---|---|
| R-001 | **所有可能超过数秒的操作必须入队**，接口不得同步等待完成（[`PRD.md`](../01-product/PRD.md) §4.3 约定 1）；同步接口只允许用于轻量查询 |
| R-002 | 任务状态**以控制面记录为权威**；agent 只上报进度与阶段，**不决定**任务终态 |
| R-003 | 同一资源的操作**互斥**：按 `(resource_type, resource_id)` 加锁，后到任务保持 `pending` 直至锁释放 |
| R-004 | **影响面大的操作全局串行**：迁移（跨节点）与存储池变更同一时刻只允许一个（§9 Q-002） |
| R-005 | 每个下发指令携带**幂等键**（`idempotency_key`，唯一索引）；agent 据此去重，网络重放**不得**导致重复执行 |
| R-006 | 节点失联时，该节点上 `running` 的任务转为 **`unknown`**，**不得**判定为失败；节点重连后由对账收敛为真实结论（[`ARCHITECTURE.md`](../02-architecture/ARCHITECTURE.md) §4.4） |
| R-007 | `pending` 任务的取消：直接置 `canceled`；`running` 任务的取消：置 `cancel_requested` 并下发取消信号，由 agent 尽力停止后回报；**超时未回报保持 `running`**，不谎报已取消 |
| R-008 | **取消不算失败**，`canceled` 与 `failed` 是并列终态，各自参与筛选与统计 |
| R-009 | `params` 与 `result` **必须脱敏**后存储与展示（口令、密钥、令牌一律不落库）；失败原因不得包含内部堆栈 |
| R-010 | 任务的**归属过滤**沿用 [`f-1-06-authorization.md`](f-1-06-authorization.md)：`tenant` 只可见自己发起的任务，`admin` 可见全部 |
| R-011 | 每个任务必须记录 `dispatched_at`（下发）与 `last_reported_at`（agent 最近上报），用于区分「排队耗时」与「通道/执行耗时」 |
| R-012 | 长流程的**失败点与回滚范围必须在任务定义中声明**（F-7-06）；未声明回滚范围的任务不允许进入实现 |
| R-013 | **实时通道只推送、不承载命令**；所有写操作仍走普通 HTTP 接口（单向通道，避免双向状态同步复杂度） |
| R-014 | 实时通道的订阅范围必须与**权限一致**：`tenant` 不得通过订阅参数获取他人资源的变更 |
| R-015 | 前端**断线重连后必须全量对账**（重新拉取当前状态），不能只依赖增量补齐（可能丢事件） |
| R-016 | 终态任务**默认保留 30 天**，可配置；清理只允许删除**终态**任务，`pending` / `running` / `unknown` 一律不可清理 |

## 4. 边界与异常

| 场景 | 触发条件 | 期望行为 |
|---|---|---|
| 重复提交 | 用户重复点击 / 网络重试 | 幂等键去重；同一幂等键重复入队返回**已有任务**而非新建 |
| 同资源并发 | 两个请求操作同一 VM | 后者保持 `pending`，按入队顺序串行执行；界面显示「排队中」 |
| 全局串行冲突 | 迁移进行中又有存储池变更 | 后者排队；**不并发**执行（R-004） |
| 执行中节点失联 | 心跳超时 | 任务转 `unknown`；界面标注「状态未知，等待节点恢复」，**不显示为失败** |
| 节点重连 | agent 上报运行态快照 | 对账并收敛 `unknown` 任务：已完成 → `success`，未完成 → `failed` 或按定义重试 |
| 取消时机过晚 | 任务已进入终态后请求取消 | 拒绝并提示「任务已结束」 |
| 取消无响应 | agent 未回报取消结果 | 保持 `running` 并继续等待；超时后提示「取消请求已下发，任务仍在结束中」 |
| 任务执行中控制面重启 | 控制面进程重启 | `pending` 任务恢复执行；`running` 任务不重复下发（靠幂等键与对账），必要时转 `unknown` 后收敛 |
| 阶段可重试 | 宿主成功、来宾阶段失败 | `task_stage.retryable` 为真时允许**单独重试该阶段**，不重跑整个任务 |
| 实时通道断线 | 网络抖动 / 服务重启 | 前端 5s 重连；重连后**全量对账**；界面显示「已断开·重连中(n)」 |
| 通道订阅越权 | `tenant` 订阅他人资源 | 拒绝订阅（403）或静默过滤（只推自己的）；一律**不推**他人数据 |
| 会话失效 | 令牌失效 | 通过 `session_expired` 事件通知；前端统一跳登录并保留回跳地址 |
| 任务量过大 | 短时间大量入队 | 队列按并发上限执行，其余排队；界面显示排队位置 |
| 清理时误选进行中任务 | 清理请求包含非终态任务 | 拒绝该部分并说明原因，**不静默跳过** |

## 5. 数据与接口

### 5.1 数据变更

| 实体 | 变更 | 说明 |
|---|---|---|
| `task` | **复用现有字段** | `type`、`idempotency_key`、`status`（含 `unknown`）、`resource_type/id`、`owner_id`、`params`、`progress`、`current_stage`、`result`、`error`、`cancel_requested`、`dispatched_at`、`last_reported_at` 等（[`DATA_MODEL.md`](../02-architecture/DATA_MODEL.md) §4.11） |
| `task_stage` | **复用现有字段** | `seq`、`key`、`name`、`status`、`message`、`retryable`、`retry_of_stage_id`（§4.12） |
| `audit_log` | 复用 | 任务取消、清理、阶段重试需记录 |

> **无需新增迁移**。注意 `task` 表的既有约束：同一资源的互斥由**应用层加锁**，不依赖数据库。

### 5.2 接口

登记至 [`API.md`](../03-api/API.md)：

| 方法 | 路径 | 说明 |
|---|---|---|
| GET | `/api/v1/tasks` | 任务列表（按状态 / 类型 / 资源 / 时间筛选，归属过滤） |
| GET | `/api/v1/tasks/:id` | 任务详情（含参数、结果与阶段时间线） |
| POST | `/api/v1/tasks/:id/cancel` | 请求取消（需二次验证的场景由前端先走 428） |
| DELETE | `/api/v1/tasks` | 清理终态任务（按条件，拒绝含非终态） |
| GET | `/api/v1/events/{channel}` | **SSE 实时通道**，`channel` ∈ `vm-list` / `vm-detail` / `tasks` / `host-metrics` |

**实时通道设计**（与 [`FRONTEND.md`](../02-architecture/FRONTEND.md) §6.1 对应）：

| 通道 | 推送节奏 | 断线策略 | 失焦策略 |
|---|---|---|---|
| `vm-list` | 2s 增量 | 5s 重连 + 全量对账 | 保持 |
| `vm-detail` | 3s 全量 | 5s 重连 + 全量对账 | **10s 断开**，聚焦立即重连并重置速率基准 |
| `tasks` | 事件驱动（阶段变更、终态） | 5s 重连 + 补齐未完成任务 | 保持 |
| `host-metrics` | 5s | 5s 重连 + 全量对账 | 保持 |

**公共约定**：

- 每 15s 发送一次注释心跳（`: ping`）以维持连接并探测断线；
- 事件类型（`event:`）与通道对应，便于前端分发；
- 通道使用 **HttpOnly Cookie 认证**（`f-1-01` Q-008 的决策直接受益：`EventSource` 无法自定义请求头，Cookie 自动携带，无需为 SSE 单独设计认证）；
- 单页最多同时建立 **2 条** SSE 连接（[`FRONTEND.md`](../02-architecture/FRONTEND.md) §6.7 性能预算）。

## 6. 非功能要求

| 类别 | 要求 |
|---|---|
| 一致性 | 任务状态以控制面为权威；节点失联**不得**判定业务失败 |
| 幂等 | 幂等键唯一约束 + agent 侧去重，网络重放不重复执行 |
| 性能 | SSE 消息处理 < 5ms（[`FRONTEND.md`](../02-architecture/FRONTEND.md) §6.7）；进度上报需节流，避免高频写库 |
| 可靠性 | 控制面重启后 `pending` 任务可恢复；`running` 任务不重复下发 |
| 安全 | `params` / `result` 脱敏；订阅范围与权限一致；清理只能删终态 |
| 可观测性 | 排队耗时（`created_at` → `dispatched_at`）与执行耗时（`dispatched_at` → `finished_at`）可区分 |

## 7. 验收标准

- [ ] AC-01：触发重操作的接口**立即返回**任务标识，不等执行完成
- [ ] AC-02：同一 VM 的第二个操作在第一个完成前保持 `pending`，不并发执行
- [ ] AC-03：迁移与存储池变更**全局串行**（同时只跑一个）
- [ ] AC-04：同一幂等键重复入队**不产生**第二个任务
- [ ] AC-05：执行中节点失联 → 任务转 `unknown`，界面**不显示为失败**
- [ ] AC-06：节点重连后，`unknown` 任务被收敛为 `success` 或 `failed` 并给出结论
- [ ] AC-07：`pending` 任务取消后状态为 `canceled`，且**不计入失败统计**
- [ ] AC-08：`running` 任务取消后下发取消信号；未回报时**不谎报**为已取消
- [ ] AC-09：任务参数与结果中的口令 / 令牌被脱敏，数据库中**查不到**明文
- [ ] AC-10：`tenant` 只能看到自己发起的任务；`admin` 可见全部
- [ ] AC-11：SSE 通道断线后 5s 内重连，且重连后状态与真实值一致（无残留脏数据）
- [ ] AC-12：`vm-detail` 通道在页面失焦 10s 后断开，聚焦后立即重连
- [ ] AC-13：会话失效时收到 `session_expired` 事件，前端跳登录并保留回跳地址
- [ ] AC-14：清理请求包含非终态任务时被拒绝并说明原因
- [ ] AC-15：`tenant` 无法通过订阅参数获取他人资源的变更事件
- [ ] AC-16：控制面重启后，`pending` 任务恢复执行且未重复下发已完成的任务

## 8. 测试要点

| 类型 | 用例 |
|---|---|
| 正常路径 | 入队 → 执行 → 阶段推进 → 终态推送 |
| 并发 | 同资源并发、全局串行冲突、队列积压 |
| 幂等 | 重复提交、网络重放、控制面重启后重放 |
| 失联与对账 | 执行中节点掉线 → `unknown`；重连 → 收敛结论 |
| 取消 | `pending` 取消、`running` 取消、终态后取消被拒 |
| 实时通道 | 断线重连、全量对账、失焦断开、心跳维持、慢客户端积压 |
| 权限 | 任务列表归属过滤；订阅越权 |
| 脱敏 | 参数与结果中不出现明文凭据 |
| 清理 | 只删终态；误选非终态被拒 |

## 9. 关键决策记录

| 编号 | 决策 | 理由 | 备选与否决原因 |
|---|---|---|---|
| Q-001 | 队列实现为**数据库持久化（`task` 表）+ 进程内调度**，不引入消息中间件 | 单控制面单体架构；`task` 表本身要作为权威状态被查询（F-7-02），引入 MQ 会形成「两处真相」且增加运维面 | 引入 Redis / RabbitMQ：为一个单体控制面增加独立中间件，运维成本与一致性复杂度都不划算；纯内存队列：重启即丢任务 |
| Q-002 | 锁分两级：**按资源键互斥**（同一 VM）+ **全局串行**（迁移与存储池变更） | 同一 VM 并发操作必然冲突；迁移与存储变更影响面涉及多节点与全局存储，并发执行风险高 | 全部全局串行：吞吐不可接受；全部按资源锁：迁移这类跨资源操作没有合适的单一资源键 |
| Q-003 | 幂等键由**控制面生成**并随指令下发，agent 侧去重 | 控制面是任务权威，幂等键必须在入队时即确定，才能覆盖「入队 → 下发」之间的一切重放 | agent 生成：无法防止入队侧重复；不设幂等键：网络重放会导致重复执行（如重复建盘） |
| Q-004 | 节点失联时任务转 **`unknown`**，不判失败；由重连对账收敛 | 失联 ≠ 失败。若判失败，可能把一个实际成功的操作标记为失败并触发错误回滚 | 判为失败：会造成误回滚与数据损坏；保持 `running`：无法向用户表达「结果未知」 |
| Q-005 | 取消与失败是**并列终态**，`canceled` 不计入失败 | 用户主动取消与系统失败的责任与后续动作完全不同（失败需排查，取消不需要） | 取消记为失败：污染失败率指标，误导运维 |
| Q-006 | `running` 任务取消采用**下发信号 + 等待回报**，超时不谎报 | 强行标记已取消会让用户误以为资源已释放，而实际可能仍在创建中 | 立即标记取消：状态与实际不符，可能引发后续操作冲突 |
| Q-007 | 实时通道用 **SSE** 而非 WebSocket | 需求是**单向**推送（服务端 → 前端）；SSE 在浏览器侧自动重连、实现简单、可穿透多数代理 | WebSocket：双向能力本场景用不到，且需自行实现重连与心跳；轮询：无法满足 2s 级别的列表刷新预算 |
| Q-008 | 通道按**用途拆分**为 4 个独立端点，而非单端点多事件 | 各通道的心跳与失焦策略不同（详情需失焦断开、列表需保持），单连接无法独立控制生命周期 | 单端点多事件：失焦策略无法按通道独立生效 |
| Q-009 | 实时通道认证复用 **HttpOnly Cookie** | `EventSource` 无法自定义请求头，Cookie 自动携带；这正是不把令牌放在内存/`localStorage` 的额外收益（`f-1-01` Q-008） | 查询参数传令牌：令牌会进入访问日志与浏览器历史，泄漏风险高 |
| Q-010 | 断线重连后**必须全量对账**，不只依赖增量补齐 | 断线期间的事件可能永久丢失（服务端不保证重放），只补增量会留下永久脏状态 | 纯增量补齐：需要服务端保存事件历史与游标，复杂且仍可能丢；因此按「增量推送 + 重连全量」组合 |
| Q-011 | 终态任务默认保留 **30 天**，只允许清理终态 | 保留期需覆盖「故障追溯」的常见窗口；未完成任务被清理会造成状态永久悬挂 | 永久保留：无限增长；立即清理：故障后无法追溯 |
