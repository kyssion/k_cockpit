## 1. 背景与目标

### 1.1 背景

认证解决「你是谁」，授权解决「你能做什么」。[`API.md`](../03-api/API.md) §4 要求「每个数据访问接口都要做归属校验（防止越权访问他人数据）」。

本能力是 M2 全部资源类功能的横切前提——虚拟机、存储、网络资源都要按归属隔离，且**不允许各模块自建一套判定**（[`CAPABILITY_MAP.md`](../01-product/CAPABILITY_MAP.md) §4：跨切面能力有唯一实现）。

### 1.2 目标

- 建立**两类角色**的能力边界，并在**中间件统一收敛**（PRD F-1-06 明确要求）；
- 资源按**归属**隔离：普通用户只能查看与操作自己名下的资源，管理员可查看与代管全部资源；
- 越权访问**不泄漏资源是否存在**；
- 越权尝试**可审计**。

### 1.3 不做什么（范围外）

| 不做 | 原因 |
|---|---|
| 自定义角色、角色权限配置界面 | 产品需求只定义两类角色（PRD F-1-06），当前无此需求 |
| 以他人身份操作（impersonation） | 会让审计失真，见 §9 Q-005 |
| 用户管理（创建 / 封禁 / 配额） | F-1-07、F-1-08（P1，M3） |
| 高风险操作二次验证（428） | F-10-01、F-10-02（另有规格）——**授权与二次验证是两件事**：前者判「能不能」，后者判「要不要再确认一次」 |
| 字段级权限（如隐藏某字段） | 当前需求为接口级与资源级 |

## 2. 用户与场景

```text
作为 普通用户，
我希望 只能看到并操作自己的虚拟机与资源，
以便 我的资源不被他人误操作。

作为 管理员，
我希望 能查看与代管全部资源，
以便 处理用户求助与清理遗留资源。
```

## 3. 功能描述

### 3.1 角色与能力边界

角色取值为**固定枚举**（`user.role`）：`admin` 与 `tenant`。

| 能力域 | `admin` | `tenant` |
|---|---|---|
| 用户管理（F-1-07）、配额设置（F-1-08） | ✅ 全部 | ❌ |
| 节点管理（F-6-*） | ✅ 全部 | ❌ |
| 系统设置（F-9-01） | ✅ 全部 | ❌ |
| 审计日志（F-1-12） | ✅ 全部 | ❌ |
| 模板管理（F-3-01~05） | ✅ 全部 | ❌ |
| 存储池管理（F-5-01、F-5-02） | ✅ 全部 | ❌ |
| 虚拟机（F-2-*） | ✅ 全部 | **仅自己名下**（受配额约束） |
| 网络资源（VPC / 安全组 / 端口转发 / 公网 IP） | ✅ 全部 | **仅自己名下** |
| 个人存储（F-5-03~05） | ✅ 全部 | ✅ 自己 |
| 安全中心（F-1-11） | ✅ 自己 | ✅ 自己 |
| 任务中心（F-7-02） | ✅ 全部 | **仅自己发起** |

**说明**：
- 「仅自己名下」= 资源的 `owner_id` 等于当前用户；
- 「全部」= 不受 `owner_id` 限制；
- 表中未列出的新能力，实现时必须**先在本表登记归属**，不允许默认放开。

### 3.2 判定流程

```text
请求 → 认证中间件（f-1-01）：解析令牌 → 校验会话 → 注入当前用户到 context
     → 授权中间件：按路由声明所需角色判定（不足则 403）
     → 处理函数：数据访问统一经「归属过滤」函数构造查询
       （admin 不过滤；tenant 强制追加 owner_id = 当前用户）
     → 单条资源访问：查不到即返回 404（不区分「不存在」与「无权限」）
```

### 3.3 业务规则

| 编号 | 规则 |
|---|---|
| R-001 | 角色为**固定枚举** `admin` / `tenant`（`user.role`），**不支持自定义角色**；新增角色须先新建 ADR |
| R-002 | 授权判定**统一在中间件与数据访问层收敛**，禁止各 handler 自行拼装权限判断（PRD F-1-06） |
| R-003 | 角色要求通过**路由注册时声明**（而非在 handler 内部判断），使「哪些接口需要什么角色」可被集中审查 |
| R-004 | 资源归属过滤**在数据访问函数内强制注入**：`tenant` 的查询一律追加 `owner_id = 当前用户`，`admin` 不加此条件 |
| R-005 | 单条资源访问（详情 / 编辑 / 删除 / 操作）查不到或不属于自己 → **一律返回 404**，不返回 403（不泄漏资源是否存在） |
| R-006 | 角色不足（如 `tenant` 调用管理类接口）→ 返回 **403**（接口本身的存在不是秘密，无需隐藏） |
| R-007 | 资源的**创建**必须写入 `owner_id = 当前用户`，不允许由前端传入 `owner_id` |
| R-008 | 管理员以**自身身份**操作他人资源，**不做身份切换**；审计中记录操作人 = 管理员，资源归属不变（§9 Q-005） |
| R-009 | 越权尝试（403 与 404 两类）**均记入审计**（F-1-12），但**不向请求方**透露判定细节 |
| R-010 | **前端隐藏不构成安全边界**：菜单与按钮的角色可见性仅为体验优化，后端对每个接口独立判定；任何依赖前端隐藏来保护的数据都视为缺陷 |
| R-011 | 授权判定所需的用户角色**每次请求从数据库读取**（或读缓存时需保证失效及时），**不**从令牌载荷取（令牌不含角色，见 `f-1-01-auth-session.md` R-004） |
| R-012 | 配额（F-1-08）与授权是**两道独立判定**：有权限不代表未超配额；两者都要通过才放行 |

## 4. 边界与异常

| 场景 | 触发条件 | 期望行为 |
|---|---|---|
| 未认证 | 无令牌 / 令牌失效 | 401（由认证中间件处理，非本规格） |
| 角色不足 | `tenant` 访问管理类接口 | 403，附统一错误码 `PERMISSION_DENIED` |
| 访问他人资源 | `tenant` 请求他人 VM 的详情 / 操作 | **404**，与「资源不存在」表现完全一致 |
| 资源确实不存在 | 任意角色请求不存在的 ID | 404，**与上一条表现一致**（不可区分） |
| 列表接口 | `tenant` 查询资源列表 | 只返回自己名下的；**不返回总数中包含他人资源的计数** |
| 创建时伪造归属 | 前端在请求体中传入 `owner_id` | **忽略该字段**，一律以当前用户为准（R-007） |
| 管理员操作租户资源 | `admin` 对他人 VM 执行电源操作 | 允许；审计记录操作人为管理员 |
| 资源归属变更 | 未来可能的「转移归属」 | 不在本规格；如需要须先定义权限与审计规则 |
| 角色被变更 | 用户从 `tenant` 提升为 `admin` | 下一次请求即生效（R-011，每次读库或及时失效缓存） |
| 用户被封禁 | `status = banned` | 认证层已拒绝（`f-1-01` R-011）；授权层不再单独处理 |
| 并发操作同一资源 | 两个请求同时操作同一 VM | 由任务队列按资源加锁（F-7-01），非本规格职责 |

## 5. 数据与接口

### 5.1 数据变更

| 实体 | 变更 | 说明 |
|---|---|---|
| `user` | **复用** | `role`（`admin` / `tenant`）、`status` 已就绪（[`DATA_MODEL.md`](../02-architecture/DATA_MODEL.md) §4.1） |
| 各资源表 | **复用** | 归属字段 `owner_id`（如 `vm.owner_id` 及索引 `idx_vm_owner_id`）已就绪 |
| `audit_log` | 复用 | 越权尝试需记录（F-1-12） |

> **无需新增迁移**。若后续需要「资源转移归属」或自定义角色，须先补数据模型与 ADR。

### 5.2 接口

**本规格不新增对外接口**——授权通过中间件与查询过滤实现，不影响接口形状。

对既有接口的影响：

| 影响 | 说明 |
|---|---|
| 错误码 | 新增使用 `PERMISSION_DENIED`（403）与「资源不存在」（404）两类既有错误码（[`API.md`](../03-api/API.md) §3.3） |
| 列表接口 | 响应中的 `total` 必须与过滤后的结果集一致，**不得**返回全局总数 |
| 所有写接口 | 请求体中的 `owner_id` 字段**一律忽略**（若存在） |

## 6. 非功能要求

| 类别 | 要求 |
|---|---|
| 安全 | 越权不泄漏存在性；前端隐藏不作为安全边界；归属由服务端强制注入 |
| 性能 | 角色与归属判定不得引入额外 N+1 查询；归属过滤应走已有索引（如 `idx_vm_owner_id`） |
| 可维护性 | 权限矩阵（§3.1）是**唯一事实来源**；新增能力必须在此登记 |
| 可观测性 | 越权尝试可审计、可统计 |

## 7. 验收标准

- [ ] AC-01：`tenant` 访问管理类接口（如用户管理）返回 403
- [ ] AC-02：`tenant` 请求他人 VM 的详情，返回 **404**，与请求不存在的 ID **表现完全一致**（状态码与响应体）
- [ ] AC-03：`tenant` 的资源列表**只含**自己名下的资源
- [ ] AC-04：`tenant` 列表响应的 `total` 与返回条目数口径一致，不含他人资源
- [ ] AC-05：创建资源时在请求体传入 `owner_id`，该字段被**忽略**，落库归属为当前用户
- [ ] AC-06：`admin` 可查看与操作任意用户的资源
- [ ] AC-07：`admin` 操作他人资源后，审计中的操作人为 `admin` 本人，且资源 `owner_id` 未改变
- [ ] AC-08：越权尝试（403 与 404）均产生审计记录
- [ ] AC-09：用户角色由 `tenant` 变更为 `admin` 后，**下一次请求**即获得管理员能力（无需重新登录）
- [ ] AC-10：前端隐藏的菜单对应的接口，用 `tenant` 令牌直接调用仍被拒绝（证明后端独立判定）
- [ ] AC-11：归属过滤走索引，列表查询在数据量增长时无全表扫描（可通过执行计划验证）

## 8. 测试要点

| 类型 | 用例 |
|---|---|
| 正常路径 | `admin` 全量访问；`tenant` 访问自己的资源 |
| 越权 | `tenant` 访问他人资源（详情 / 编辑 / 删除 / 列表）；横向越权与纵向越权各覆盖 |
| 存在性隐藏 | 他人资源 与 不存在资源 的响应**逐字节一致** |
| 归属注入 | 请求体伪造 `owner_id`；查询参数伪造归属；批量操作中混入他人资源 ID |
| 角色变更 | `tenant` → `admin` 与反向变更后的即时生效 |
| 审计 | 越权尝试、管理员代管均正确记录 |
| 性能 | 归属过滤使用索引；无 N+1 |

## 9. 关键决策记录

| 编号 | 决策 | 理由 | 备选与否决原因 |
|---|---|---|---|
| Q-001 | 权限模型采用**固定角色枚举**（`admin` / `tenant`），不引入角色表与权限表 | 既有数据模型（43 张表）本就没有角色/权限表；PRD 只定义两类角色且无自定义需求。引入权限表需要配套管理界面、缓存与迁移，属过度设计 | 数据库驱动 RBAC：当前无需求支撑，且会显著抬高实现与维护成本；如需自定义角色，届时新建 ADR 评估 |
| Q-002 | 角色判定在**中间件 + 路由声明**收敛；归属过滤在**数据访问层**强制注入 | PRD F-1-06 明确要求「统一在中间件收敛」；把归属过滤下沉到查询层可避免各 handler 手写条件时漏加（漏加即为越权漏洞） | 在各 handler 内判断：分散、易漏、难以集中审查——正是 PRD 要避免的 |
| Q-003 | 「他人资源」返回 **404**，「角色不足」返回 **403** | 前者要隐藏资源存在性；后者隐藏无意义（接口本身公开存在），且 403 更利于排查 | 一律 403：泄漏了「该 ID 的资源存在」这一信息；一律 404：把权限问题伪装成不存在，排查成本高 |
| Q-004 | 归属过滤通过**统一的数据访问函数**注入，而非各查询自行拼接 | 越权漏洞最常见成因就是「某个查询忘了加归属条件」；收敛到一处可被集中审查与测试 | 逐处手写：无法保证一致性，且新增接口时容易遗漏 |
| Q-005 | **不做 impersonation**（身份切换），管理员以自身身份操作 | 身份切换会让审计记录失真（「谁做的」变成被模拟用户），且事后无法区分是用户本人还是管理员所为 | 支持 impersonation：审计与责任归属复杂化，当前无此需求 |
| Q-006 | 越权尝试**记审计但不提示请求方** | 越权尝试是安全事件，需要可追溯；向请求方提示判定细节会帮助攻击者探测边界 | 仅返回错误不记审计：安全事件不可见；返回详细原因：泄漏内部规则 |
| Q-007 | 令牌**不含角色**，角色每次请求读取（或读缓存但保证失效及时） | 角色变更需即时生效；把角色放进令牌会导致「已降权的用户凭旧令牌继续拥有管理员能力」——这正是 `f-1-01` R-004 的设计意图 | 角色入令牌：变更延迟直到令牌过期，存在提权窗口 |
| Q-008 | 归属过滤后，列表的 `total` **必须**为过滤后计数 | 若返回全局总数，`tenant` 可据此推断出他人资源数量，构成信息泄漏 | 返回全局总数：泄漏他人资源规模 |
