# 功能规格

> 状态：生效
> 最后更新：2026-09-15
> 关联：[`../01-product/PRD.md`](../01-product/PRD.md)（功能编号与优先级）· [`../01-product/ROADMAP.md`](../01-product/ROADMAP.md)（阶段与里程碑）· [`../01-product/CAPABILITY_MAP.md`](../01-product/CAPABILITY_MAP.md)（能力依赖）

本目录存放**单个功能的详细规格**。一份规格对应一个可独立开发与验证的功能单元。

---

## 1. 为什么需要功能规格

- 把「产品需求」翻译成「可实现的工程描述」。
- **给 AI 提供精确的任务输入**：没有规格，AI 会自行臆造细节。
- 明确边界与验收标准，减少返工。
- 作为测试用例的来源，保证「实现」与「验收」一致。

---

## 2. 何时写规格

满足以下**任一**条件：

- 功能涉及多个模块或多次提交
- 存在需要与相关方确认的细节
- 有复杂的业务规则或边界情况
- 计划交由 AI 实现

**可以不写规格的**：文案调整、样式微调、单文件小改动。

---

## 3. 文件命名

- 使用小写英文 + 连字符：`user-login.md`、`order-export.md`
- 与功能编号对应（若有）：`f-001-user-login.md`
- 一份文件一个功能，**不要在一个文件里塞多个功能**。

---

## 4. 规格与其它文档的关系

```
docs/01-product/PRD.md        我要解决什么问题（产品视角，宏观）
        ↓ 拆解
docs/07-specs/<功能>.md        这个功能具体怎么做（工程视角，微观）
        ↓ 约束
docs/02-architecture/          受架构与技术选型约束
docs/03-api/API.md             涉及接口时需同步更新
docs/06-decisions/             不得违背既有 ADR
```

**原则**：规格是 PRD 的下游，是代码的上游。规格中**不重复**架构文档已有的内容，用链接引用。

---

## 5. 规格状态

| 状态 | 含义 | AI 可否开始实现 |
|---|---|---|
| Draft | 草稿，细节仍在讨论 | 否 |
| Ready | 已确认，无遗留疑问 | 是 |
| In Progress | 实现中 | — |
| Done | 已完成并验收 | — |
| Cancelled | 已取消 | 否 |

**规则**：状态不是 `Ready` 的规格，AI **不应**开始实现，应先澄清疑问。

## 7. 编写要求

一份合格的规格必须做到：

- **无歧义**：避免「适当」「尽量」「合理」这类模糊表述。
- **可验证**：每条验收标准都能用测试或明确的步骤验证。
- **自包含**：AI 只读这一份文件也能理解要做什么（可链接引用架构文档，但不依赖口头信息）。
- **明确边界**：写清楚不做什么。
- **覆盖异常**：说明依赖失败、输入非法、并发冲突时的行为。
- **标注待决**：未定的细节用 `<!-- TODO -->` 标注，**不要留空**。

## 9. AI 使用说明

AI 代理在实现某个功能前，应：

1. 读取对应的规格文件，确认状态为 `Ready`。
2. 若发现歧义、缺失或与既有 ADR 冲突，**先提出疑问**，不要自行假定。
3. 按规格的「验收标准」编写测试，确保实现与验收一致。
4. 实现完成后，将规格状态更新为 `Done`。
