## 1. 背景与目标

### 1.1 背景

高危操作（删除、格式化、对外暴露、网络拆分）一旦误执行，结果**不可逆或影响可达性**。二次验证是这类操作的最后一道人工闸门。

但这里有一个**必须平衡的矛盾**：

> 验证太少 → 误操作无法拦截；验证太多 → 用户产生「验证疲劳」，条件反射式通过，防线形同虚设。

[`PRD.md`](../01-product/PRD.md) F-10-02 因此明确要求：**查询类与普通创建类不列入清单**。

### 1.2 目标

- 建立**判定口径**（F-10-02），使「哪些操作要验证」有唯一标准，不靠个人判断；
- 建立**统一流程**（F-10-01）：判定 → 返回需验证 → 完成验证 → **自动重试原请求**；
- 前端**单飞加锁**、**防死循环**，避免验证流程自身出问题；
- 清单**由后端下发**，前端不硬编码第二份；
- 避免验证疲劳：只在真正不可逆或被暴露的操作上验证。

### 1.3 不做什么（范围外）

| 不做 | 归属 |
|---|---|
| 输入侧防护、响应安全头、错误脱敏 | F-10-03 / F-10-04（P1，M3） |
| 密码策略与泄露检测 | F-10-05（P2，M4） |
| 公网访问与开发模式开关 | F-10-06（P1，M3） |
| 2FA 的**绑定与管理**（恢复码、TOTP 设置） | F-1-04 / F-1-11（另有规格） |
| 危险操作**自身的回滚能力** | 由各能力实现，本规格只负责「拦一道」 |

**关于 F-10-07 与 F-10-08**（均为 P0）：

- **F-10-07**（危险网络变更可回滚）已在 [`f-4-01-network-backend.md`](f-4-01-network-backend.md) R-007 落实；
- **F-10-08**（进程与资源操作的归属校验）是**横切约束**，由涉及宿主侧进程/资源操作的能力规格落实（如网络、存储）。其通用规则：**禁止仅凭端口或 IP 判断归属**，必须以 PID 文件、服务单元或「进程名 + 参数指纹」校验。参考项目曾因此误杀自身进程（见 [`08-reference/qvmconsole/README.md`](../08-reference/qvmconsole/README.md) §4.4）。

## 2. 用户与场景

```text
作为 用户，
我希望 在执行危险操作前被要求确认身份，
以便 误点或凭据被盗时不会直接造成不可逆后果。

作为 用户，
我希望 确认一次后紧接着的这次操作能顺利执行，
以便 不必反复验证同一件事。
```

## 3. 功能描述

### 3.1 判定口径（F-10-02）

**判定标准**：该操作是否**会造成不可逆结果**或**影响可达性**。

| 类别 | 示例 | 是否列入 |
|---|---|---|
| **删除类** | 删除虚拟机（含连盘删除）、删除存储池、批量删除、删除用户、删除模板、磁盘分区删除 | ✅ |
| **格式化 / 重建类** | 格式化磁盘并挂载、创建分区（可能覆盖数据）、系统重装、快照恢复 | ✅ |
| **暴露类** | VNC 对外暴露、公网 IP 绑定、防火墙开放端口、端口转发开通 | ✅ |
| **网络拆分** | 物理网卡接入网桥（迁移宿主默认路由）、交换机模式变更、网络后端切换 | ✅ |
| **宿主级** | 宿主内核参数调优、密钥轮换（使全部令牌失效）、agent 撤销注册 | ✅ |
| **迁移 / 救援** | 跨节点迁移、救援模式启停 | ✅ |
| **查询 / 查看类** | 列表、详情、日志、指标、导出（只读） | ❌ |
| **普通创建类** | 创建虚拟机、创建模板、创建用户 | ❌ |
| **可逆的配置变更** | 改备注、改分组、改端口转发规则（可撤销） | ❌ |

**防疲劳原则**：

- 同一操作**不因「文件大小 / 数量」而改变判定**（如删 1 台与删 10 台同属删除类，都是一次请求一次验证）；
- 批量操作**整体验证一次**，不逐项验证；
- **不把「重要但可逆」的操作列入**——可逆性由配套的确认与回滚机制承担。

### 3.2 统一流程（F-10-01）

```text
1. 前端发起操作请求
2. 后端判定为高风险且当前会话无有效许可
   → 返回 428（Precondition Required）+ 需要的验证方式
3. 前端弹出验证框（2FA 动态码 / 恢复码 / 邮箱验证码）
4. 用户提交验证码 → POST 验证接口
5. 验证通过 → 服务端签发**一次性许可**（短有效期）
6. 前端**原样重放原请求**（携带许可）→ 操作正常执行
```

### 3.3 交互细节

与 [`FRONTEND.md`](../02-architecture/FRONTEND.md) §6.2 一致，要点：

| 环节 | 要求 |
|---|---|
| 验证框 | 按后端返回的可用方式渲染（不硬编码「只支持 TOTP」） |
| 单飞加锁 | 同一时刻**只允许一个**验证流程；重复触发时复用当前流程，不叠加弹窗 |
| 防死循环 | **重试仅一次**；若重试后仍返回 428，直接报错而非再次弹框 |
| 失败提示 | 给出**剩余尝试次数**；次数用尽后按限流处理 |
| 重放 | 验证通过后**原请求参数原样重放**（含请求体与幂等键） |
| 注册/未绑定 2FA | 按后端返回的方式降级（如邮箱验证码），若无可用方式则明确提示需先绑定 |

### 3.4 业务规则

| 编号 | 规则 |
|---|---|
| R-001 | 高风险判定**集中在一处**（F-10-02 的清单），各能力**不得**自行决定；新增操作时先判定是否入清单 |
| R-002 | 清单**由后端作为唯一事实来源下发**，前端只渲染与提示，**不允许硬编码第二份**（[`FRONTEND.md`](../02-architecture/FRONTEND.md) §6.5） |
| R-003 | 判定在**服务端**执行；前端可以提前提示「此操作需要验证」，但**前端不提示不等于不验证**（前端不构成安全边界） |
| R-004 | 验证通过后签发**一次性许可**：短有效期（建议 2 分钟）且**消费即失效**；批量操作为一次请求，故只需一次许可 |
| R-005 | 许可**绑定会话与发起者**，不可转让、不可跨会话使用 |
| R-006 | 验证流程必须具备：**单飞加锁、重试仅一次、失败计数与限流**（[`FRONTEND.md`](../02-architecture/FRONTEND.md) §6.2） |
| R-007 | 验证方式支持 **TOTP 动态码 / 一次性恢复码 / 邮箱验证码**；具体可用方式由后端按用户实际绑定情况返回 |
| R-008 | 使用**恢复码**验证时，该码**用后即废**，并提示剩余恢复码数量（恢复码总数有限，需引导用户关注） |
| R-009 | 验证失败**统一文案**，不区分「码错误」与「码过期」的细节；**记账但不提示**具体判定细节 |
| R-010 | 验证尝试**按用户限流**（与登录限流独立计数），触发后返回 429 并给出可重试时间 |
| R-011 | 高风险操作的**审计必须记录「已通过二次验证」**这一事实（验证方式与时间），便于事后追溯 |
| R-012 | 通过 **API Key** 调用的请求**不触发交互式验证**——这是显式取舍（[`PRD.md`](../01-product/PRD.md) F-1-10）：API 无法交互，且 Key 本身即长期凭据；**但必须在 API 文档中明示**该差异 |
| R-013 | 会话失效（登出、被撤销、安全信息变更）时，**未消费的许可一并失效** |
| R-014 | 前端在收到 428 时**不得**静默重试或自动提交验证码；必须由用户完成验证 |
| R-015 | 许可的**有效期与消费语义必须在服务端强校验**，前端展示的倒计时仅供参考 |

## 4. 边界与异常

| 场景 | 触发条件 | 期望行为 |
|---|---|---|
| 用户未绑定 2FA | 无 TOTP、无已验邮箱 | 返回可用的降级方式；若确实无可用方式 → 明确提示「需先绑定二次验证方式」，并给出跳转 |
| 恢复码用尽 | 恢复码全部消费 | 提示恢复码已用尽并引导重新生成（需先通过其他方式验证） |
| 验证码错误 | 提交错误码 | 统一失败文案 + 剩余尝试次数；计入限流计数 |
| 验证码过期 | TOTP 时间窗过期 | 同上（不额外提示「过期」，避免探测） |
| 重试后仍 428 | 许可未被识别（并发/过期） | **不再弹框**，直接报错并提示「验证状态已失效，请重试操作」（防死循环） |
| 并发多个高风险操作 | 用户同时开两个标签删东西 | 各自独立请求；许可**一次性**，先到先得，后者需重新验证（避免一个许可被复用多次） |
| 许可在有效期内被重放 | 攻击者截获许可并重复使用 | 消费即失效 → 第二次使用被拒 |
| 操作本身失败 | 验证通过但业务失败 | 许可已消费，需重新验证（不复用）；错误原因按业务返回 |
| 会话中途失效 | 验证期间登出 | 验证请求被拒（401）；需重新登录 |
| API Key 调用高风险操作 | 无交互能力 | 不触发验证（R-012），但**记审计并标注「API Key 调用」** |
| 大量 428 请求 | 恶意探测 | 按会话/IP 限流；不影响正常用户 |

## 5. 数据与接口

### 5.1 数据变更

| 实体 | 变更 | 说明 |
|---|---|---|
| `security_challenge` | **复用现有表** | 验证挑战的存储（[`DATA_MODEL.md`](../02-architecture/DATA_MODEL.md) 已建该表；字段级以其定义为准） |
| `user` | **复用** | `totp_enabled`、`totp_secret_enc`、`recovery_codes_hash` 提供验证方式判定（§4.1） |
| `audit_log` | 复用 | 高风险操作需记录「已通过二次验证（方式 + 时间）」 |

> **无需新增迁移**。许可（grant）为**短生命周期的服务端状态**，建议存于内存或 `security_challenge`，**不引入新的持久表**（避免为 2 分钟有效期的数据建表）。

### 5.2 接口

登记至 [`API.md`](../03-api/API.md)：

| 方法 | 路径 | 说明 |
|---|---|---|
| GET | `/api/v1/security/high-risk-policy` | 高风险操作清单与判定口径（供前端渲染提示，**只读**） |
| POST | `/api/v1/auth/risk-verification` | 提交验证码，换取一次性许可 |

**约定**：

- 被保护的操作接口在需要验证时返回 **428**，响应体包含：需要的验证方式列表、`challenge_id`、提示文案；
- 验证接口成功时返回**一次性许可**（`grant`）与有效期；前端在**重放原请求**时通过请求头携带；
- 许可**不在响应中回显验证码**，也不记录验证码明文；
- `high-risk-policy` 返回的是**口径与清单**，不是「当前用户是否需要验证」——后者由具体操作请求的响应决定。

## 6. 非功能要求

| 类别 | 要求 |
|---|---|
| 安全 | 判定在服务端；许可一次性且绑定会话；恢复码用后即废；尝试限流；会话失效即失效 |
| 体验 | 批量操作只验证一次；验证框复用而非叠加；失败给出剩余次数 |
| 可靠性 | 许可校验不依赖前端；重试仅一次，不产生死循环 |
| 可观测性 | 验证通过、失败、限流、API Key 豁免均需可查（审计 + 日志） |
| 性能 | 判定应为常量级查表，不引入额外查询；许可存储不宜落库（短生命周期） |

## 7. 验收标准

- [ ] AC-01：高风险操作在无许可时返回 **428**，并给出可用验证方式
- [ ] AC-02：验证通过后**原请求可成功重放**，无需用户重复填写表单
- [ ] AC-03：查询类与普通创建类操作**不触发**验证
- [ ] AC-04：批量删除**只验证一次**（不逐项验证）
- [ ] AC-05：许可**消费即失效**——同一许可第二次使用被拒
- [ ] AC-06：许可超过有效期后失效
- [ ] AC-07：许可**绑定会话**——在其他会话中不可用
- [ ] AC-08：使用恢复码后该码失效，且提示剩余数量
- [ ] AC-09：验证失败给剩余尝试次数，超过阈值触发限流（429）
- [ ] AC-10：重试后仍返回 428 时**不再弹框**（防死循环）
- [ ] AC-11：会话失效后未消费的许可同时失效
- [ ] AC-12：审计中记录「已通过二次验证」的方式与时间
- [ ] AC-13：API Key 调用**不触发**交互式验证，但审计标注「API Key 调用」
- [ ] AC-14：前端未提示的操作，服务端仍会验证（证明判定在服务端）
- [ ] AC-15：高风险清单由后端下发，前端无硬编码副本（可通过改动后端清单验证前端行为随之变化）

## 8. 测试要点

| 类型 | 用例 |
|---|---|
| 判定 | 逐类操作验证是否入清单（删除 / 格式化 / 暴露 / 网络拆分 / 宿主级 vs 查询 / 普通创建 / 可逆变更） |
| 流程 | 428 → 验证 → 重放成功；表单数据完整保留 |
| 许可 | 一次性、有效期、会话绑定、并发竞争 |
| 验证方式 | TOTP、恢复码（含用尽）、邮箱验证码；无可用方式时的提示 |
| 限流 | 连续失败触发限流；限流期间正确码也不放行 |
| 防死循环 | 重试仍 428；重复触发验证框 |
| 豁免 | API Key 调用；审计标注 |
| 失效 | 会话登出 / 被撤销 / 安全信息变更后许可失效 |

## 9. 关键决策记录

> 阶段性方案，演进约定见 [`README.md`](README.md) §5.1。

| 编号 | 决策 | 理由 | 备选与否决原因 |
|---|---|---|---|
| Q-001 | 判定口径采用「**不可逆 或 影响可达性**」双条件 | 这两类后果无法靠事后补救挽回（数据没了、机器连不上了），其余问题都可以用确认弹窗与回滚解决 | 按「操作重要性」判定：主观、无法一致执行；全量验证：导致验证疲劳，防线失效 |
| Q-002 | **查询与普通创建类不列入**清单 | 创建虚拟机是可逆的（删除即可），把它列入只会让用户对验证麻木——这是 PRD F-10-02 明确的反面案例 | 从宽列入：验证疲劳，真正危险的操作反而被忽略 |
| Q-003 | 用 **428 Precondition Required** 表达「需先完成验证」 | 语义准确（请求缺少必要前置条件），且与 401（未认证）、403（无权限）区分明确——前端可据此精确分支，不必解析业务错误码 | 用 403 携带业务码：与权限不足混淆；用自定义 200 + 业务码：破坏状态码语义，前端拦截器难以统一处理 |
| Q-004 | 许可**一次性 + 短有效期**，而非「一段时间内免验证」 | 一次性把滥用窗口压到最小；而批量操作本就是一次请求，体验不受影响 | 时间窗内多次免验证：用户验证一次后可连续执行任意多次删除，等于没有二次确认 |
| Q-005 | 验证方式**由后端按用户实际绑定情况返回**，前端不硬编码 | 用户可能只绑了 TOTP、或用完了恢复码；硬编码会导致前端弹出无法完成的验证 | 前端固定三种方式：会在未绑定场景下把用户卡死 |
| Q-006 | 恢复码**用后即废**并提示剩余数量 | 恢复码本质是一次性凭据；不失效等于留下永久后门 | 可重复使用：一旦泄漏即长期有效 |
| Q-007 | 验证失败**不区分错误类型** | 区分「码错误」与「码过期」会帮助攻击者判断猜测方向 | 精细提示：泄漏判定细节 |
| Q-008 | API Key 调用**豁免交互式验证**，但显式记录取舍 | API 无交互能力；Key 本身是长期凭据，其风险由生成时的权限与 IP 绑定控制。**必须明示**，避免用户误以为 API 调用也受保护 | 强制 API 也二次验证：不可实现；静默豁免：用户不知情 |
| Q-009 | 许可状态**不落持久表** | 有效期仅 2 分钟且一次性，落库会带来无谓的写入与清理负担 | 建表存储：为短生命周期数据引入表结构与清理任务，属过度设计 |
| Q-010 | 重试**仅一次**，仍 428 则报错 | 无限重试会在许可失效等异常下形成死循环（反复弹框），用户无法退出 | 允许重试：死循环风险；不重试：正常流程也被打断 |
