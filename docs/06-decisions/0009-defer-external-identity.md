## 背景

PRD 的 F-1-13（外部身份源：LDAP / OIDC / Passkey 登录与组映射）标为 P2，并在功能表里注明"是否纳入见 §4.4"；而 §4.4 的待确认清单里**没有为它立过项**——也就是说，这条能力从需求登记起就一直挂着"做不做"这个未决问题。

第四轮差距收尾（G-42 ~ G-54）之后，它是路线图上剩余的最后一条 P2 功能项，必须给出明确结论，而不是继续悬着。

## 决策

**暂不纳入。** F-1-13 从"待确认"改为"本期不做"，触发条件满足时再评估。

理由：

1. **部署形态不匹配。** 本项目的定位是自建自用的虚拟化管理面板（AGENTS.md 项目概览），典型部署是"一个组织、少数管理员 + 若干租户"。本地账号 + 邮箱找回 + TOTP 两步验证 + 邀请注册这条链路已经完整，外部身份源解决的问题（多组织共享身份、避免多套面板各记一套密码）在当前形态下不存在。
2. **收益远小于攻击面。** 引入 LDAP / OIDC 意味着：一套新的认证协议栈与回调处理、组映射的权限模型扩展（外部组 ↔ 内部角色）、身份提供方故障时的降级登录路径、以及外部 IdP 凭据的保管。每一条都是长期维护面；而它替换掉的只是"用户在面板里再设一个密码"。
3. **无法验证的交付等于没交付。** 开发与演示环境没有真实的 LDAP / OIDC 服务，接入实现只能靠 mock 自测——一个**恰好不能 mock**（它是纯控制面能力，却依赖外部真实系统）的功能，在无验证条件下交付，违背"不留下半成品"的项目红线。
4. **数据模型不需要预留。** 用户表的身份字段（邮箱、TOTP）与角色模型不受影响——将来纳入时是**增加**一种登录方式，而不是改写既有模型，现在预留任何字段都是 YAGNI。

## 触发重新评估的条件

- 出现**多组织共享**一套面板的真实部署需求（外部组映射成为硬需求）；
- 部署组织已有强制性的身份集中管理规范（内部已有 IdP，禁止应用自管密码）；
- 出现 Passkey 一类的**防钓鱼凭据**需求且评估认为收益超过本地密码 + TOTP 的组合。

满足任一条时，新建 ADR 论证协议选择（OIDC 优先，LDAP 次之）与组映射模型，再排期实现。

## 后果

- PRD §4.4 登记本结论，F-1-13 标注"本期不做（ADR-0009）"；
- 路线图 M4 的 P2 功能清单相应收敛，剩余工作聚焦多节点与热迁移（已于本轮落地）；
- 登录链路维持现状：本地账号 + 多阶段登录 + TOTP + 邮箱找回 + 邀请注册。
