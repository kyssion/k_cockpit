## 背景

本项目要集中管理多台 KVM/QEMU 宿主机上的虚拟机，并规划多租户与网络治理能力。参考项目 QVMConsole 的网络实现（分析见 [`REFERENCE_QVMCONSOLE.md`](../08-reference/qvmconsole/features.md)）表明：

- 其 **VPC 逻辑交换机（VLAN 隔离）、端口安全（反欺骗/端口隔离/包速率）、带宽限速（OpenFlow meter + QoS）、端口镜像、公网 IP 绑定（防伪造流表）** 等能力，**全部依赖可编程交换机**；
- Linux 默认网桥（libvirt `virbr0`）无法以可维护的方式提供同等能力；
- OVS 已是主流 Linux 虚拟化平台的既有组件，资料与工具链成熟。

约束：
- 目标运行环境为 Linux 宿主机；控制面本身需保持平台无关（开发在 Windows）。
- 项目规范要求「不过度设计」：不引入用不到的能力，但也**不能为了图省事而放弃规划中确有需求的网络能力**。

---

## 决策

k_cockpit 采用 **Open vSwitch** 作为虚拟网络后端，用于承载多租户隔离与网络治理能力。具体约定：

1. **可插拔**：网络后端抽象为独立接口，提供「基础模式」（Linux 网桥 / NAT）与「增强模式」（OVS）。不具备 OVS 的环境仍可运行基础功能，不因缺少 OVS 而不可用。
2. **能力探测 + 降级**：仅当宿主机具备所需能力（OpenFlow13 协商、meter 的 `pktps`/`burst`、ingress policing 字段等）时才启用对应增强功能；不满足则降级并明确提示，不强行执行。
3. **不阻断主流程**：OVS 配置失败不得导致服务不可用，应降级并暴露可诊断/可修复的入口。
4. **危险操作可回滚**：把宿主机**物理网卡接入 OVS 网桥**（会迁移宿主默认路由，配置失误可致宿主机断网）的操作，必须支持回滚、需显式确认，**禁止在无人值守流程中无保护执行**。

---

## 理由

- **能力匹配**：上述网络能力是产品规划的一部分，Linux 网桥无法以可维护方式支撑，自研等价能力属于重复造轮子。
- **生态成熟**：OVS 被主流虚拟化/云平台广泛采用，长期可维护；宿主机侧依赖清晰（`openvswitch-switch`）。
- **有先例可循**：参考项目已验证「OVS + VLAN tag + dnsmasq + NAT」这套组合在 KVM 场景可行，并暴露了需要规避的坑（端口冲突、物理口入桥断网、运行态需自愈），降低了我们的试错成本。
- **符合选型原则**：可替换性由「可插拔后端」保证——OVS 仅为增强模式，基础模式不依赖它。

---

## 备选方案

### 方案 A：仅使用 Linux 网桥（`bridge` / `iproute2`）

- 优势：零额外系统依赖、配置简单、无「物理口入桥断网」风险。
- 劣势：无可编程流表；VLAN 隔离、per-port QoS、端口镜像、端口安全需拼装大量 iptables/tc 规则，难以原子化与维护。
- 否决原因：无法以可维护的方式支撑规划中的多租户与网络治理能力。**但保留为基础模式**（无 OVS 环境的降级路径）。

### 方案 B：iptables + tc，不引入 OVS

- 优势：不新增组件。
- 劣势：规则分散、缺乏端口级抽象、镜像与端口隔离实现困难、排障成本高。
- 否决原因：等同于方案 A 的劣势，且更易失控。

### 方案 C：采用 SDN / CNI 类方案（Calico、eBPF 等）

- 优势：能力更强、性能好。
- 劣势：面向容器编排设计，与 libvirt/KVM 虚拟机网络场景不匹配；引入额外控制面与学习成本。
- 否决原因：场景不匹配，违背「匹配问题、不过度设计」。

---

## 影响

### 正面

- 获得可编程网络能力，支撑多租户隔离、带宽治理、端口安全与镜像。
- 与主流虚拟化实践一致，宿主机侧依赖与文档成熟。
- 通过「可插拔 + 能力探测」，避免了对 OVS 的强绑定。

### 负面 / 代价

- 宿主机新增 OVS 依赖，运维与排障复杂度上升。
- 网络配置失误（尤其是物理口入桥、默认路由迁移）**可导致宿主机断网**。
- OVS 运行态在重启后不会自动恢复，需要启动时的自愈/对账逻辑。
- 与 libvirt 自带 dnsmasq 存在端口（53/67）竞争，需要明确的接管与冲突处理策略。

### 需要的配套调整

- `TECH_STACK.md` 增加「网络虚拟化」选型行并关联本 ADR —— **待本 ADR 转为 `Accepted` 后执行**。
- `ARCHITECTURE.md` 补充网络抽象，明确「基础模式 / 增强模式」与能力探测策略。
- OVS 相关系统依赖需在部署文档中登记；危险的网络变更操作需在设计阶段就定义回滚方案。
