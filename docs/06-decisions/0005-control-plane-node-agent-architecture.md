# 0005. 采用控制面 / 节点代理（agent）架构

## 背景

系统需要**集中管理多台 KVM/QEMU 宿主机**。参考项目 QVMConsole 的做法是"每台宿主机部署一套完整面板"，控制面通过**目标面板 API** 与 **宿主机 root SSH** 两条通道操作远端。这套做法在本项目中带来四个问题：

1. **凭据面过大**：控制面必须持有每台宿主机的 root SSH 凭据（或等价高权限凭据），一处泄漏等于全部宿主机失守。
2. **能力探测脆弱**：靠"SSH 进去逐项跑命令"（9 项检查）判断节点是否可用，依赖远端命令环境，慢且容易误判。
3. **组件重复**：每台目标机都要跑完整面板（含 Web 资产与数据库），升级与排障面成倍放大。
4. **平台差异上浮**：发行版、包名、命令参数的差异会一路泄漏到控制面代码里。

约束：
- 宿主机常位于**内网 / NAT 之后**，控制面不保证能主动连入；
- 控制面须保持**平台无关**（见 [ADR-0004](0004-adopt-openvswitch-as-network-backend.md) 的约束）；
- 项目规范要求「能力探测 + 降级」「单步失败不阻断主流程」「危险操作可回滚」（`AGENTS.md` 第 5 节）。

---

## 决策

采用**控制面 / 节点代理（agent）架构**，共 9 条约定：

1. **角色划分**
   - **控制面**：持有**期望态**与元数据（配置、用户与权限、配额、任务编排、聚合展示、审计）；
   - **agent**：部署在每台宿主机，是**唯一直接操作 libvirt/KVM 与宿主系统的角色**，也是**运行态的唯一来源**。

2. **通信方向**：agent **主动连回控制面**建立长连接（反向通道）；控制面不主动连 agent，**不需要宿主机开放入站端口**。同网段可选用"直连模式"（控制面连 agent 的 HTTPS 端口）作为性能优化，**反向通道为默认且必需**。

3. **协议形态**：控制面与 agent 之间走**领域操作接口**（创建/开关机/快照/挂盘/迁移/取指标…）与**任务指令 + 进度流**；**不转发 libvirt 原始 RPC**。承载协议（gRPC 系）在实现阶段另定，不在本 ADR 内钉死。

4. **职责边界（大数据不出宿主机）**
   - 控制面**不直连 libvirt、不在宿主机执行命令、不搬运磁盘数据**；
   - agent 执行全部宿主侧动作：虚拟机、磁盘与快照、迁移的**数据搬运**、网络与防火墙、存储池、抓包、指标采集与聚合；
   - 镜像、磁盘、指标原始采样等大数据**只在 agent 侧处理**，回传控制面的只有**聚合结果与进度**。

5. **注册与信任**：控制面生成**一次性注册令牌** → agent 首次启动用令牌注册 → 换取**客户端证书（mTLS）** → 后续长连接；令牌用后失效、可撤销。

6. **能力自报**：agent 在启动与重连时**自探测并上报能力**（虚拟化命令与版本、网桥与 OVS 能力、IOMMU、目录与权限等），控制面据此决定功能可用性与降级路径，**不再由控制面远程探测**。

7. **断连行为**：agent **本地自治**——已运行的虚拟机不受影响；控制面侧标记节点离线，其数据带"**陈旧时间戳**"语义，**不误判为故障**；agent 重连后**对账上报**。

8. **版本兼容**：agent 上报自身版本与协议版本；控制面须兼容 **N-1 个 agent 协议版本**。agent 自动升级**不在本期**实现（先手工升级，预留升级入口）。

9. **控制面自身宿主机**：同样以 agent 方式纳管（**零特例**），避免"本地直连 + 远端走 agent"两套分支。

---

## 理由

- **安全性**：控制面不再持有宿主机 root 凭据，攻击面小一个数量级；agent 只暴露**领域操作白名单**，不是通用命令执行，不会被当作跳板。
- **适配性**：反向长连接天然适配内网/NAT 后的宿主机，也不需要为每台机器签发公网证书。
- **平台解耦**：平台相关代码全部沉到 agent，控制面保持平台无关——与 ADR-0004 的方向一致。
- **能力探测更可靠**：从"远端 SSH 猜测"变成"agent 自报"，结果准确、速度快，且**天然支持降级决策**（不满足能力 → 关闭对应增强功能并提示）。
- **组件轻量**：节点侧只需一个 agent 二进制（无前端、无独立数据库），纳管 = 在物理机上跑一条安装命令。
- **有先例可循**：参考项目 kite 的 Cluster Agent 已验证"反向隧道 + 领域客户端"这套模式可行，降低了我们的试错成本。

---

## 备选方案

### 方案 A：沿用参考项目的「完整面板 + API/SSH 双通道」

- 优势：参考项目已实现，功能细节可直接对照；不新增组件。
- 劣势：控制面持有全部宿主机的 root SSH 凭据；探测靠远端命令；节点侧要跑完整面板；平台差异上浮。
- **否决原因**：安全模型不可接受（root 凭据集中化），且与"控制面平台无关"的约束冲突。

### 方案 B：控制面直连各宿主机 libvirt（无 agent）

- 优势：少一个组件。
- 劣势：libvirt 的 TLS 认证与网络暴露配置复杂；跨版本兼容由控制面承担；宿主机侧的网络/存储/抓包等操作仍需 SSH 或远程执行；控制面被 libvirt 版本绑死。
- **否决原因**：等于把方案 A 的问题换成另一种形式，且丢失"能力自报"与"大数据不出宿主机"两个关键收益。

### 方案 C：agent 只做反向隧道（纯字节转发，不做领域接口）

- 优势：agent 极简，控制面可复用现有 libvirt 客户端代码。
- 劣势：libvirt 原始 RPC 穿过隧道，版本差异与协议演进直接落在控制面；agent 无法做本地聚合、幂等与重试；隧道变成"通用透传"后安全边界模糊。
- **否决原因**：把复杂度留在了最难演进的一侧；且与"能力自报""本地自治"两条约定不兼容。

---

## 影响

### 正面

- 控制面**不持有宿主机凭据**，安全边界清晰（用户面靠 JWT/API Key，节点面靠 mTLS）。
- 节点侧组件单一（一个 agent），部署、升级、排障都简单。
- 能力探测下沉，控制面只做决策，**降级路径统一**。
- 大数据不出宿主机，控制面带宽与存储压力可控。
- 控制面与 agent 可分别演进，**兼容策略明确（N-1）**。

### 负面 / 代价

- 新增一个有状态组件需要维护：进程守护、证书签发与轮换、版本兼容、升级入口。
- **控制面数据在节点离线时是陈旧的**，必须在界面与接口上显式表达（否则会误导操作）。
- 指标不能全量回传，**agent 侧必须做聚合与降采样**，否则带宽与数据库都会失控。
- 迁移等跨节点动作需要"控制面编排、agent 之间传数据"的协调机制，比单机实现复杂。
