# 架构决策记录（ADR）

> 状态：生效
> 最后更新：<!-- TODO: YYYY-MM-DD -->

本目录记录项目的**重大技术决策及其理由**，采用 ADR（Architecture Decision Record）形式。

---

## 1. 为什么需要 ADR

- 回答「**为什么这么选**」，而不只是「选了什么」。
- 防止后人（以及 AI）反复推翻已验证过的决策。
- 提供决策的历史脉络：当时的信息、约束与权衡。
- **对 AI 尤其重要**：AI 不了解历史，容易提出已被否决的方案。ADR 是它的必要约束。

---

## 2. 何时需要写 ADR

满足以下**任一**条件即应记录：

- 影响多个模块的架构选择
- 引入或替换核心技术组件（框架、数据库、中间件）
- 对外接口风格或契约的重大变更
- 数据模型的关键设计（如分库分表、软删除策略）
- 安全方案选型（鉴权方式、加密方案）
- 有意接受的技术债（并说明偿还计划）
- 被明确否决的方案（记录否决理由，避免重复讨论）

**不需要 ADR 的**：局部实现细节、可轻易回退的小选择、纯风格偏好。

---

## 3. 文件命名

```
NNNN-动词短语.md
```

- `NNNN`：四位序号，从 `0001` 开始，**连续递增，不复用**。
- 使用小写英文与连字符。
- 示例：
  - `0001-record-architecture-decisions.md`
  - `0002-use-xxx-as-primary-database.md`
  - `0003-adopt-rest-for-public-api.md`

---

## 4. 状态流转

```
提议(Proposed) → 接受(Accepted) → [被取代(Superseded) | 废弃(Deprecated)]
```

| 状态 | 含义 |
|---|---|
| Proposed | 正在讨论，尚未生效 |
| Accepted | 已生效，必须遵守 |
| Superseded | 被更新的 ADR 取代（需注明被哪个取代） |
| Deprecated | 不再推荐，但暂未替代 |

**铁律**：
- 已生效的 ADR **只增不改**。修改决策必须**新建** ADR，并让旧的标记为 `Superseded`。
- 禁止删除 ADR 文件。
- 禁止直接编辑他人已 Accepted 的 ADR 内容（修正错别字除外）。

---

## 5. 撰写要求

一份 ADR 必须包含：

1. **背景**：面临什么问题，有哪些约束
2. **决策**：最终选了什么
3. **理由**：为什么这样选
4. **备选方案**：考虑过哪些，为何否决
5. **影响**：正面与负面的后果，需要做的配套调整
6. **状态与日期**

要求：
- 决策要**可执行**，避免模棱两可（「视情况而定」不是决策）。
- 记录**权衡**而非只记优点。
- 使用简洁语言，控制在一到两屏内。

新建 ADR 时复制以下结构：

```markdown

- 状态：Proposed
- 日期：YYYY-MM-DD
- 决策人：<姓名>
- 关联：<相关文档 / Issue / 其他 ADR>

## 背景

<面临的问题、约束、当前状况>

## 决策

<明确说明选定了什么>

## 理由

<为什么这样选>

## 备选方案

### 方案 A：<名称>
- 优势：
- 劣势：
- 否决原因：

## 影响

### 正面
-

### 负面 / 代价
-

### 需要的配套调整
-

## 参考

- <链接 / 资料>
```
