# 0007. 远程操作先以 Mock 落地，业务逻辑保持真实

## 背景

M2 需要交付「建 VM → 开机 → 控制台 → 关机 → 删除」的完整链路，涉及控制面、数据库、前端与宿主机 agent 四部分。

agent 侧的落地成本很高：需要真实的 KVM/libvirt 环境、mTLS 证书签发与轮换、gRPC 双向流、宿主机安装脚本，以及每种领域操作的宿主侧实现（创建 VM、格式化磁盘、配置 OVS……）。这些工作会长时间阻塞「业务逻辑是否完备」的验证。

同时，控制面的绝大部分复杂度**并不在宿主机操作上**，而在于：

- 任务队列的状态机、幂等、并发与取消；
- 投影（`vm` / `node` 表）与真实状态的一致性与陈旧标记；
- 授权与资源归属、审计、高风险二次验证；
- 前端的信息架构、交互与实时通道。

这些逻辑**不依赖真实宿主**即可完整实现与验证。因此本期采取：先把「页面 → 控制面 → 数据库」这条链路做完整，**agent 侧不开发，与它的交互只保留接口，由 mock 直接返回结果**。

---

## 决策

**1. agent 侧本期不开发，控制面只保留交互接口。**

控制面定义「需要节点做什么」的接口（`internal/agent`）。本期**不实现**真实 agent（gRPC 服务端、证书签发、宿主侧领域操作、安装脚本），也不实现「模拟 agent 行为」的假 agent。

**2. mock 只负责「有返回值」，不模拟执行行为。**

mock 实现直接返回预设结果，**不模拟耗时、进度推进、失败注入、离线与上报**。理由：本期目标是让业务逻辑完备，而模拟逻辑本身是将来会被丢弃的代码。

**代价（有意接受）**：执行失败、超时、节点离线等异常分支在接入真实 agent 前不会被触发，需在与真实节点联调时集中验证。

**3. 业务代码只依赖接口，不得感知实现。**

业务层只调用 `agent.Client`，不知道背后是 mock 还是 gRPC。出现 `if mock` 即为设计违规。这样接入真实节点时只需替换实现，**业务代码零改动**。

**4. 接口按需扩展，不预先设计完整协议。**

不一次性定义几十个方法去覆盖全部领域操作，而是**在实现每个业务能力时，按需向接口添加所需方法**。避免为尚未实现的能力臆测协议形态——真实的协议细节（字段、语义、错误分类）应在实现该能力时确定。

**5. 与 ADR-0005 的关系不变。**

真实实现仍将走 gRPC 双向流与 mTLS（[`ADR-0005`](0005-control-plane-node-agent-architecture.md)）。本 ADR 只调整**本期交付顺序与范围**，不改变目标架构。

---

## 理由

| 选择 | 理由 | 备选与否决原因 |
|---|---|---|
| 在接口层 mock，业务逻辑全真实 | 这是唯一无法在无宿主机环境下真实执行的边界；其余逻辑都能真跑 | 在业务层 mock：业务逻辑永远没被真正验证 |
| mock 只返回结果，不做行为模拟 | 模拟逻辑（耗时、进度、失败）是**将来必被丢弃**的代码，投入产出比低 | 高保真假 agent：开发量大，且模拟出的行为未必与真实一致，容易给出虚假的安全感 |
| 接口按需扩展 | 领域操作的真实语义要在实现时才能确定，提前设计容易臆造 | 一次性定义完整协议：大概率与最终实现不符，返工成本更高 |
| 业务代码不感知 mock | 保证接入真实节点时业务零改动 | —— |

## 后果

**正面**

- 页面、数据库、业务逻辑可端到端跑通并验证，不依赖宿主机环境；
- 不产生「将来会丢弃的模拟代码」，投入集中在真正需要完善的业务逻辑上；
- 接真实 agent 时只需新增一个 `Client` 实现（见 ADR-0005 的协议设计）。

**负面 / 代价**

- **异常分支未经验证**：执行失败、超时、节点离线、任务卡住等场景，在联调前只存在于代码里，未被真实触发过。接入真实节点时必须专门覆盖这些分支；
- mock 的返回是**我们假设的形状**，可能缺少真实 agent 才有的字段与状态，接真实时需校准数据结构，但业务代码不需要改。

**约束**

- 业务代码不得感知 mock（第 3 条），代码评审需检查；
- 接口方法在扩展时，若影响多个调用方，需同步更新本 ADR 与相关规格。
