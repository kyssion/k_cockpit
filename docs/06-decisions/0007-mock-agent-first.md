# 0007. 远程操作先以 Mock Agent 落地，业务逻辑保持真实

## 背景

M2 需要交付「建 VM → 开机 → 控制台 → 关机 → 删除」的完整链路，涉及控制面、数据库、前端与宿主机 agent 四部分。

但 agent 侧的落地成本很高：需要真实的 KVM/libvirt 环境、mTLS 证书签发与轮换、gRPC 双向流、容器或物理机上的安装脚本，以及最麻烦的——**每种领域操作的宿主侧实现**（创建 VM、格式化磁盘、配置 OVS、抓包……）。这些工作会长时间阻塞「业务逻辑是否完备」的验证。

同时，控制面的绝大部分复杂度**并不在宿主机操作上**，而在于：

- 任务队列的状态机、幂等、并发与取消；
- 投影（`vm` / `node` 表）与真实状态的一致性与陈旧标记；
- 授权与资源归属、审计、高风险二次验证；
- 前端的信息架构、交互与实时通道。

这些逻辑**不依赖真实宿主**即可完整实现与验证。

因此本期采取：**先把「页面 → 控制面 → 数据库」这条链路做完整，agent 交互以 mock 落地**。

---

## 决策

**1. Mock 的边界在传输层（agent 通道），不在业务层。**

```text
控制面业务逻辑（真实）
  任务队列 / 投影更新 / 授权 / 审计 / 风险验证
        ↓ 下发指令
  Transport 接口（抽象）
        ├── grpcTransport   ← 将来：真实 gRPC 双向流（ADR-0005）
        └── mockTransport   ← 现在：进程内假 agent
                ↓ 模拟执行（延迟、进度、失败、离线）
                ↓ 经 ReportHandler 上报
控制面业务逻辑（真实）—— 处理上报、推进任务、更新投影
```

**2. mock agent 必须经由「与真实 agent 相同的入口」上报。**

假 agent **不得**直接写数据库，而是调用控制面处理上报的同一套入口（心跳、状态快照、任务进度、任务结果）。这样：

- 「收到上报 → 更新投影 → 推进任务 → 推送实时通道」这段逻辑是**真实的**；
- 将来接真实 agent 时，这段逻辑无需改动。

**3. mock 与真实实现通过配置切换，且不允许混用。**

配置项（如 `AGENT_TRANSPORT=mock|grpc`）在启动时决定，运行期不可切换。同一进程内不得对不同节点使用不同实现，避免出现「一半真一半假」的不可复现状态。

**4. mock 的行为必须模拟真实的不确定性。**

至少覆盖：执行耗时与进度推进、失败、节点离线、上报延迟。**不允许**让 mock 永远立即成功——否则前端与任务状态机会在真实环境下暴露大量未处理分支。

**5. 业务代码中不得出现「是否为 mock」的分支。**

业务层只依赖 `Transport` 接口，不知道实现是 mock 还是 gRPC。出现 `if mock` 即为设计违规。

**6. mock 的能力清单与 f-6-01 的能力上报语义一致。**

假 agent 同样上报「声明式能力清单」，控制面据此判断某操作是否可用——这条链路与真实一致，避免将来出现「界面可用但节点不支持」的落差。

---

## 理由

| 选择 | 理由 | 备选与否决原因 |
|---|---|---|
| 在传输层 mock | 这是唯一无法在无宿主机环境下真实执行的边界；其余逻辑都能真跑 | 在业务层 mock：业务逻辑永远没被真正验证，「逻辑完备」无从谈起 |
| 假 agent 走真实上报入口 | 保证「上报 → 投影 → 任务 → 实时通道」这段最复杂的逻辑是真实代码 | 假 agent 直写数据库：等于把最需要验证的链路绕过去了 |
| 配置切换、不混用 | 避免不可复现的中间状态 | 运行期动态切换：难以排查问题 |
| mock 模拟失败与延迟 | 前端与状态机的异常分支需要被真实触发过 | 永远成功：异常分支到接真实 agent 时才第一次运行 |

---

## 后果

**正面**

- 页面、数据库、业务逻辑可端到端跑通并验证，不依赖宿主机环境；
- 接真实 agent 时只需新增一个 `Transport` 实现，业务代码零改动；
- 前端可以在真实 API 契约下开发，不需要自己造 mock 数据；
- 任务的失败、重试、离线等分支在开发期即被覆盖。

**负面 / 代价**

- mock 的行为是**我们假设的真实行为**，可能与真实 agent 有偏差——接真实 agent 时必须做一次校准，重点核对：任务状态迁移时机、进度上报粒度、错误分类；
- mock 让「一切正常」看起来太容易，容易掩盖真实环境下的时序问题（如上报丢失、乱序）。

**约束**

- 业务代码不得感知 mock（第 5 条），代码评审需检查；
- mock 的行为需与 [`f-6-01`](../07-specs/f-6-01-node-onboarding.md) 的协议语义保持同步；协议能力变更（如新增流式转发）时，mock 需一并更新，否则会掩盖集成问题。
