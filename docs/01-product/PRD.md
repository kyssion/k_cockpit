> 优先级：`P0` 必须做，`P1` 应该做，`P2` 可以做。
> 编号规则：`F-<域序号>-<域内序号>`，域序号与 §4.1 各小节一一对应；`参考` 列指向 [`../08-reference/qvmconsole/capabilities.md`](../08-reference/qvmconsole/capabilities.md) 的对应小节。

### 4.0 范围与来源

**来源**：本节的功能面**对齐参考项目 QVMConsole**——能力清单见 [`capabilities.md`](../08-reference/qvmconsole/capabilities.md)（用户可见能力）、交付面明细见 [`functional-inventory.md`](../08-reference/qvmconsole/functional-inventory.md)（模块 × 接口/任务/高风险操作）。参考项目只提供"**有哪些能力、边界在哪、踩过哪些坑**"，实现方式与架构由我们自定（见 [`../08-reference/README.md`](../08-reference/README.md) §2）。

**范围原则（2026-09-14 确认）**：本系统**全面覆盖 QVMConsole 的能力面，不做范围裁剪**。`P0`/`P1`/`P2` 只表示**交付顺序**，不表示"不做"——全部条目都在系统范围内。与参考项目能力面的逐项覆盖对照见 [`CAPABILITY_MAP.md`](CAPABILITY_MAP.md) §6。

**本期范围**：集中管理多台 KVM/QEMU 宿主机的**虚拟化管理控制台**——虚拟机生命周期、镜像模板、网络、存储、用户与配额、节点、任务与监控。

**明确边界（本设计不含）**：

| 边界 | 说明 |
|---|---|
| Kubernetes 管理 | 参考项目 `kite` 覆盖的能力面（多集群看板、Helm、AI 助手等）**不在本项目范围**（2026-09-14 确认：只做 QVMConsole 相关，kite 暂不考虑） |
| 容器 / 编排控制面 | 本系统面向虚拟机，不引入容器编排能力 |
| 已被参考项目移除的能力 | 端口转发 HTTP 探测与建站扫描、开发者监视器（QEMU Monitor）、创建向导"智能推荐"、工作台全局搜索入口等，**不实现**（依据：`capabilities.md` §7"已确认失效条目"） |
| 分布式 / 共享存储 | 存储基于宿主机本地盘与 LVM，不做 Ceph 类分布式存储与跨节点共享卷 |
| 计费与商务 | 有配额与用量口径，但不含支付、账单、订单等商务能力 |

### 4.2 与参考项目的关键差异（我们的设计决定）

| 维度 | 参考做法 | 我们的做法 | 理由 |
|---|---|---|---|
| 部署形态 | 面板与宿主机 1:1 绑定（单机部署） | 控制面与节点解耦：一个控制面管理 N 台宿主机，**每台宿主机只部署轻量 agent**（无前端、无独立数据库） | 参考项目的限制不构成我们的约束（[`../08-reference/README.md`](../08-reference/README.md) §2.3）；多节点也是"节点管理 / 迁移 / 放置"成立的前提 |
| 节点接入 | 目标面板 API + 宿主机 **root SSH** 双通道，控制面持有各节点凭据 | **agent 反向长连接** + 一次性注册令牌 + mTLS；控制面**不保存**宿主机登录凭据 | [ADR-0005](../06-decisions/0005-control-plane-node-agent-architecture.md)：凭据集中化风险不可接受，且远端探测脆弱 |
| 数据库 | SQLite 单文件 | PostgreSQL（已选型，见 `docs/02-architecture/TECH_STACK.md`） | 控制面收敛后需要并发写入、统一审计与多实例部署能力 |
| 网络后端 | 与 OVS 强绑定 | 可插拔：基础模式 + 增强模式（OVS）并按能力探测降级 | [ADR-0004](../06-decisions/0004-adopt-openvswitch-as-network-backend.md) |
| 用户模型 | 云类型二分（弹性云 / 轻量云）+ 两套并行接口（用户侧与管理侧各一套） | **建议**：角色 + 配额档位，接口一套 + 授权与字段范围过滤 | 两套接口的字段与参数范围差异会长期双倍维护；是否改为档位模型见 §4.4 |
| 运行态约束 | 前端禁用与后端校验各维护一份 | 约束矩阵作为**单一事实来源**（F-2-05），前后端同源 | 参考项目两处规则易漂移 |
| 有状态约束 | 大量按"是否运行中"分支 | 保留（虚拟化的客观约束），但把"能力探测 + 降级"作为统一模式 | F-4-01 / F-6-02 统一处理，避免每处各写一套 |
| 存储 | 本地目录 + LVM | 同（不做分布式存储） | 控制 YAGNI，见 §4.0 边界 |

### 4.3 跨功能设计约定

1. **重操作一律异步**：任何可能超过数秒的操作入任务队列（F-7-01），接口只返回任务标识。
2. **能力探测 + 降级**：依赖宿主机/虚拟化层能力的功能，由**节点 agent 自探测并上报**能力清单，控制面缓存并据此启用或降级；缺失时给出提示而非整功能不可用（[ADR-0005](../06-decisions/0005-control-plane-node-agent-architecture.md) §6）。
3. **高风险清单独立维护**：判定口径集中在 F-10-02，新增操作时先判定是否入清单，不在各处自行决定。
4. **依赖分层显式化**：每项能力依赖的系统命令与来宾侧软件登记成表，缺失时明确"整功能不可用"还是"降级"。
5. **失败与回滚先设计**：长流程在实现前先定义失败点、回滚范围与用户可见文案（F-7-06）。
6. **不做已被参考项目移除的功能**：引用功能前先确认目标版本是否真的要它（见 `capabilities.md` §7）。

### 4.4 已确认结论与待确认项

**已确认（2026-09-14）**：

| 编号 | 结论 | 说明 |
|---|---|---|
| Q-1 | **不含 Kubernetes 管理** | 只做 QVMConsole 相关能力面，`kite` 面暂不考虑（见 §4.0 边界）；系统范围以全量对齐 QVMConsole 为准，不再做裁剪 |

**待确认**：

| 编号 | 待确认 | 影响 | 建议 |
|---|---|---|---|
| Q-2 | 多租户是否本期落地 | RBAC、配额、资源归属是否进 P0 | MVP 可先"管理员单租户"，但数据模型预留归属字段，避免后期大改 |
| Q-3 | 用户模型：保留"弹性云 / 轻量云"二分，还是改为角色 + 配额档位 | 影响 F-1-06 / F-1-08 与全部接口授权 | 建议档位模型（见 §4.2） |
| Q-4 | 目标规模（宿主机数 / 虚拟机数 / 并发用户） | 决定控制面是否需要多实例、任务队列是否需外部队列 | 先按"数十节点、数千虚拟机、单实例控制面"设计 |
| Q-5 | SPICE 的开放策略（客户端需直连虚拟机端口） | 网络暴露面与防火墙规则 | 能力在范围内（F-2-09，P2）；默认关闭，仅显式开启并"对外暴露"时才放通端口 |
| Q-6 | 多架构支持范围（x86_64 / aarch64 / riscv64） | 创建向导的机型与固件联动规则、模板与镜像体系 | 建议先 x86_64 + aarch64 验证，riscv64 随架构字段一并支持但延后实测 |
| Q-7 | OVF-OVA 与磁盘导入导出的优先级 | 创建向导步骤与模板包格式 | 均在范围内（F-2-13 / F-2-14）；建议导入先于导出 |
| Q-8 | 多节点放置策略（人工指定 / 自动选择） | F-6-06 的算法口径与创建向导交互 | 建议先"人工指定 + 余量提示"，自动放置延后 |
